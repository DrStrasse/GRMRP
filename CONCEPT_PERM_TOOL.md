# Концепция: GRM Perm Tool — собственный инструмент перма пропов

**Дата:** 2026-08-13 · **Версия концепции:** 2 (детальная, готова к реализации)
**Область:** перм-система, проп-протектор, FFD/раздвижные двери, фракционные права, служебный инструмент

---

## 1. Что есть сейчас

| Подсистема | Файл | Состояние |
|---|---|---|
| Ядро перма | `lua/autorun/sh_grm_perm_entities.lua` (552 стр., v1.5.0) | Работает: `data/grm_perm_entities.json`, спавн на `InitPostEntity` + `PostCleanupMap` |

### Формат записи сегодня

```lua
{ map = "rp_test", class = "grm_keypad", model = "models/props_lab/keypad.mdl",
  pos = {x=..., y=..., z=...}, ang = {p=..., y=..., r=...}, data = {...} }
```

Плоский массив. `PERM_MAX = 256` на карту. Дедуп и поиск — класс + радиус `PERM_RANGE = 6`.

### Кто уже пользуется делегатами (важно для п. 3.4)

`grm_keypad`, `grm_scanner`, `grm_bank_vault`, `grm_bank_computer`, `grm_bank_terminal`,
`grm_money_press`, `grm_money_launderer`, кухня (3 класса), FFD-двери (`prop_physics`),
служебные компьютеры (8 классов) — итого **9 файлов**, все через `Extract[class] = fn`.
Ломать этот синтаксис нельзя.

## 2. Дефекты

### Блокирующие

**Д17. `GRM.Perm.Add` / `GRM.Perm.Remove` не существуют.**
`grm_service_tool.lua:156,210` зовёт их под `if GRM.Perm and GRM.Perm.Add then`. Grep по `lua/`:
**ноль присваиваний** `GRM.Perm.*`. Условие всегда ложно → чекбокс «Автоматически сохранять на
карте (Perm)» не делает ничего, но игроку пишется «(сохранено на карту)». После рестарта
служебный компьютер ведомства исчезает вместе с заголовком.

**П1. Перм отбирает объект у владельца.**
`spawnAll()` зовёт `PP.MarkServerEntity(ent)` для **каждой** воскрешённой записи, а
`PP.CanInteract` проверяет `IsServerEntity` **раньше** `IsOwner`. Итог: запермленная лидером
FFD-дверь после рестарта принадлежит «Серверу». Владелец не может ни физганить, ни тулить.
Запись перма вообще не хранит владельца — восстановить его неоткуда.
Парадокс: `Apply["prop_physics"]` при этом честно восстанавливает `FFD_OwnerSID64` внутрь
двери — то есть владелец в `data` есть, но протектор о нём не знает.

**П2. `/permremove` удаляет объект.** Снятие записи и `ent:Remove()` — одна операция.
«Перестать сохранять, но оставить» невозможно. Промах прицелом = потерянный объект.

### Архитектурные

**П3. Записи без идентификатора.** Поиск только по классу + 6 юнитов. Сдвинул физганом
дальше — `/permremove` говорит «записи нет», а после рестарта объект возвращается на старое
место или воскресает вторым экземпляром. Лечится только правкой json.

**П4. Один делегат на класс.** `ffd_fading_door.lua:192` присваивает
`Extract["prop_physics"]` напрямую. Перм-тулу для обычных пропов нужен тот же класс
(цвет, материал, скин, заморозка) → кто загрузился позже, тот и затёр.

**П5. Пермы едят лимит пропов.** `PP.countProps` считает все `prop_physics` персонажа,
включая запермленные. 150 запермленных дверей = игрок не может поставить ни одного пропа.

**П6. Два несогласованных списка классов** — `PERM_CLASSES` и `SERVER_CLASSES`, оба локальные,
снаружи не расширяются. Новый класс надо вписывать в два места.

**П7. Права только у суперадмина.** Лидер фракции может *поставить* служебный компьютер, но
не может его закрепить.

**П8. Нет аудита** — кто и когда запермил, в базе не хранится.

**П9. `PP.IsManaged` не существует.** `sim_prop_protect.lua:64` падает на ней (`attempt to call
field 'IsManaged'`) — тест красный целиком. Функции нет нигде в `lua/`. Тест писался под API,
которого в v2.0.0 не осталось.

### Мины — трогать нельзя

- **Свой сейв:** CCTV (`CCTV.SavePermanent`), `grm_vendor` (`data/grm_vendors/<map>.json`),
  логистика (3 класса), автоперсистентные (`grm_server_rack`, `grm_antenna`,
  `grm_radio_station`, `grm_net_console`, `grm_loudspeaker`). Двойной перм = дубли на карте.
- **Временные:** `grm_item_drop`, `grm_money_drop`, `grm_ore_chunk`, `grm_mobile_line`,
  `grm_logistics_crate`. Перм такого = вечный мусор.
- **Накопленные json на боевом сервере** — миграция обязательна, без потерь, с откатом.

## 3. Решение

```
   STOOL grm_perm_tool ─┐
   grm_service_tool    ─┼─►  GRM.Perm (публичный API)  ─►  grm_perm_entities.json (v2)
   прочие модули       ─┘           │
                                    ├─►  GRM.PropProtect  (владение, защита, лимиты)
                                    └─►  GRM.PermData     (цепочки Extract/Apply)
```

Ядро остаётся в `sh_grm_perm_entities.lua`, тул — тонкий клиент над API.

### 3.1. Публичный API `GRM.Perm` (Д17, П6)

```lua
GRM.Perm.Add(ply, ent, opts)        --> code, rec
    -- "added" | "exists" | "limit" | "quota" | "noclass" | "blacklist"
    -- | "denied" | "savefail" | "invalid"
GRM.Perm.Remove(ply, ent, deleteEnt)--> "removed" | "notfound" | "denied"
GRM.Perm.Update(ply, ent)           --> "updated" | "added" | "notfound"
GRM.Perm.IsPerm(ent)                --> bool
GRM.Perm.Info(ent)                  --> rec | nil
GRM.Perm.ListForMap(map)            --> { rec, ... }
GRM.Perm.CanManage(ply, ent)        --> bool, reason
GRM.Perm.IsPermable(ent)            --> bool, reason
GRM.Perm.RegisterClass(class, opts) --> расширение реестра снаружи
GRM.Perm.Classes, GRM.Perm.Blacklist
```

Сигнатуры `Add(ply, ent)` / `Remove(ply, ent)` подобраны **точно под существующие вызовы**
в `grm_service_tool.lua` — Д17 закрывается сам, служебный тул не правим.

`opts = { ownerKind = "server"|"character"|"faction", freeze = true, label = "" }`.

Старые `GRM.PermData.Upsert` и `UpdateEntry` сохраняются как алиасы — `sim_perm_upsert`
(14/14) обязан остаться зелёным.

### 3.2. Формат v2 и миграция (П1, П3, П8)

Файл остаётся **плоским массивом** — существующий `loadList()` читает его без изменений.
Добавляются только новые поля:

```lua
{
  -- существующие, не трогаются
  map, class, model, pos = {x,y,z}, ang = {p,y,r}, data = {...},
  -- новые
  uid       = "pm_7f3a91c4",  -- стабильный ID записи
  ownerKind = "server",       -- server | character | faction
  owner     = "",             -- CharacterKey (для character)
  ownerName = "",             -- имя на момент перма, для HUD/списка
  faction   = "",             -- имя фракции (для faction)
  freeze    = true,           -- замораживать физику при воскрешении
  label     = "",             -- подпись в /permlist
  by = "", byName = "",       -- аудит: кто запермил
  at = 1770000000,            -- когда (os.time)
}
```

**Алгоритм миграции — идемпотентный, один раз при первой загрузке:**

1. Прочитать базу. Если **все** записи имеют `uid` → миграция не нужна, выход.
2. Записать бэкап `data/grm_perm_entities.bak.<os.time>.json` **с проверкой чтением**
   (как `saveList`: записал → перечитал → сравнил). Бэкап не удался → **миграцию отменить**,
   работать со старым форматом, крик в консоль.
3. Для каждой записи без `uid`:
   `uid` = сгенерированный; `ownerKind = "server"`; `freeze = true`;
   `at = os.time()`; `by = "", byName = "migration"`.
4. Сохранить один раз. Флаг `version = 2` не в записи, а определяется по наличию `uid`.

**`ownerKind = "server"` для всех старых записей — это ровно сегодняшнее поведение**
(`MarkServerEntity` для всего). Регрессии нет by design. Откат = переименовать `.bak`.

### 3.3. Синхронизация с проп-протектором (П1, П5)

Вводится третья категория владения — между «серверным» и «своим пропом».

| Метка на энтити | Сейчас | Станет |
|---|---|---|
| `ent._grmPerm` | «серверное» **и** «не чистить» слитно | только «персистентный, не чистить» |
| `ent._grmPermKind` | — | `server` / `character` / `faction` |
| `ent._grmPermUID` | — | uid записи, точный поиск без координат |

Правки в `sh_grm_prop_protect.lua` — четыре точки, поведение по умолчанию сохраняется:

1. **`IsServerEntity`** — `_grmPerm == true` даёт «серверное», **только если** `_grmPermKind`
   пуст или `"server"`. Старые (мигрированные) пермы → `server` → как раньше.
2. **`CanInteract`** — новая ветка **между** «серверное» и «чужой проп»:

```lua
-- 2.5. Перм персонажа/фракции
if ent._grmPerm and ent._grmPermKind and ent._grmPermKind ~= "server" then
    if action == "use"    then return true end
    if action == "remove" then return false end   -- только тулом, иначе запись осиротеет
    if ent._grmPermKind == "character" then
        return PP.IsOwner(ply, ent) and PP.Cfg.ownPhysgun ~= false
    end
    return GRM.Perm.CanManage(ply, ent)            -- faction: член с правом perm_manage
end
```

3. **`countProps`** — пропускает `ent._grmPerm`: пермы не съедают `maxProps = 150`.
4. **HUD** — строка «★ ЗАКРЕПЛЁН НА КАРТЕ» + владелец (`Сервер` / имя / фракция).

`cleanupProps` и `cleanupDisconnectedOwner` уже фильтруют `_grmPerm` — не трогаем; критично
лишь, что тул ставит `_grmPerm` **для всех** видов владения, включая `character`.

**Воскрешение** (`spawnAll`) вместо безусловного `MarkServerEntity`:

| `ownerKind` | Действие |
|---|---|
| `server` | `PP.MarkServerEntity(ent)` — как сейчас |
| `character` | восстановить `GRM_PropOwnerCharacterKey` + NW-строки из `owner`/`ownerName`, `_grmPerm = true` |
| `faction` | `_grmPermKind = "faction"`, доступ у членов с `perm_manage`, остальным — как к серверному |

`freeze == false` → `EnableMotion` не выключается (для качелей, тележек и т.п.).

### 3.4. Цепочки делегатов — без правки 9 файлов (П4)

Синтаксис `Extract[class] = fn` должен остаться рабочим для всех существующих регистраций.
Решение — подменить `GRM.PermData.Extract/Apply` таблицами с метатаблицей: `__newindex`
накапливает функции в цепочку, `__index` возвращает композит.

**Проверено на LuaJIT** (`/tmp/mt_test.lua`): FFD регистрируется первым, перм-тул вторым,
тем же синтаксисом — результат `ffd сохранён: true`, `prop сохранён: true`,
`apply цепочка: ffd:5 | prop:red`, несуществующий класс → `nil`.

- `Extract` — результаты всех функций цепочки **мержатся** в одну таблицу (ключи верхнего
  уровня не пересекаются: `ffd`, `sliding`, `prop`, `computerName`, …).
- `Apply` — вызываются по очереди, каждая под `pcall`.
- Порядок загрузки перестаёт что-либо решать; `ffd_fading_door.lua` **править не нужно**.

Перм-тул регистрирует для `prop_physics` свой делегат:

```lua
data.prop = { color = {r,g,b,a}, material = "", skin = 0, bodygroups = {...},
              frozen = true, solid = true, rendermode = 0, scale = 1 }
```

### 3.5. Реестр классов и чёрный список (П6)

- `GRM.Perm.Classes` — публичный алиас `PERM_CLASSES`.
- `GRM.Perm.Blacklist` — **явный** список с человеческой причиной:
  «у CCTV собственное сохранение», «временный объект», «модуль сохраняется сам».
  Отказ приходит в чат с пояснением, а не молча.
- `GRM.Perm.RegisterClass(class)` — сторонние модули регистрируют себя сами.
- Хук `GRM_PermCanAdd(ply, ent)` — любой модуль может ветировать (`false, "причина"`).

### 3.6. Права и квоты (П7)

| Роль | Может |
|---|---|
| Суперадмин | всё, любой класс и владелец; лимит карты 256 |
| Роль с правом `perm_manage` (лидер) | `ownerKind = "faction"`, квота **32** на фракцию |
| Игрок | по умолчанию **нет**; конвар `grm_perm_players 1` → квота **8**, только свои `prop_physics` |

В `GRM.FactionPerms.Permissions` добавляется одна строка
`perm_manage = "Закрепление объектов на карте (перм)"` — право сразу появляется
в существующем UI фракционных прав, отдельный интерфейс не нужен.

### 3.7. Инструмент `grm_perm_tool` (STOOL, категория GRM)

Оформление — по образцу `grm_service_tool.lua` (`TOOL.Category = "GRM"`, `language.Add`, `BuildCPanel`).

| Ввод | Действие |
|---|---|
| **ЛКМ** | Запермить объект под прицелом; если уже запермлен — обновить позицию/угол/данные |
| **ПКМ** | Инфо в чат: класс, uid, владелец, кто и когда запермил, счётчик пермов карты |
| **R** | Снять перм. Объект по умолчанию **остаётся** на карте (лечение П2); удаление — галочкой |
| **Shift+ЛКМ** | Перм без заморозки (`freeze = false`) |

C-панель: комбобокс владельца (Сервер / Мой персонаж / Моя фракция), чекбоксы «Заморозить
физику» (вкл.) и «При снятии удалять объект» (**выкл.**), поле «Подпись», кнопки «Список
пермов», «Перезагрузить пермы», «Снять все мои пермы», справка по чёрному списку.

Оверлей, пока тул в руках: рамка и подпись «ПЕРМ · класс · владелец» над объектами в радиусе
~1200 юнитов. Данные — одним снимком `GRM_PermTool_Snapshot` при взятии тула и по кнопке
(не таймером, чтобы не грузить сеть).

### 3.8. Автообновление позиции (П3)

`PhysgunDrop` для объекта с `_grmPermUID` → дебаунс 1.5 с → обновление `pos`/`ang` по **uid**.
Подвинул запермленную дверь — новое положение сохранилось само. Координатный поиск остаётся
fallback'ом для незамигрированных записей.

### 3.9. Хуки для модулей

`GRM_PermAdded(ply, ent, rec)`, `GRM_PermRemoved(ply, class, rec)`, `GRM_PermUpdated(ent, rec)`,
`GRM_PermRestored(ent, rec)` — последний после воскрешения, чтобы сигнализация, банк и
электроника доподключили объект к своим реестрам.

## 5. Порядок работ

1. **Ядро:** API, uid, миграция + бэкап с проверкой чтением, `ownerKind`, чёрный список,
   цепочки делегатов, хуки.
2. **Тест `sim_perm_tool.lua`** (по образцу `sim_perm_upsert`, реальный файл под моком):
   миграция старой базы без потерь, идемпотентность повтора, uid-поиск после сдвига,
   квоты фракции/игрока, отказ чёрного списка, мерж двух делегатов на `prop_physics`.
3. **Протектор:** 4 правки + разбор П9 (`IsManaged` — вернуть функцию или переписать тест).
4. **Инструмент:** STOOL, C-панель, оверлей.
5. **Права:** `perm_manage`.
6. **Регрессия:** `sim_perm_upsert` (14/14 обязан остаться), `sim_ffdtools`,
   `sim_sliding_door`, `sim_prop_protect`, `sim_electronics`, `roundtrip_test`.
7. **Документация** `PERM_SYSTEM.md`, сборка `dist/`, коммит, ссылки на архивы.

## 6. Решения по умолчанию

Вопросы согласования остались без ответа, поэтому фиксирую умолчания — самые
консервативные из возможных. Любое можно изменить одной строкой.

| Вопрос | Умолчание |
|---|---|
| Кто может пермить | Суперадмин + роль с `perm_manage` (фракция, квота 32). Игрокам — выкл., включается конваром `grm_perm_players 1` |
| Кнопка R | Снимает запись, **объект оставляет**; удаление — галочкой |
| Перевод старых пермов на фракции | Команда `/permowner <фракция>` по прицелу — **делаем**, лишней не будет |
| Квоты | 256 на карту (как сейчас), 32 на фракцию, 8 на игрока |
| Старые `/permadd`, `/permremove` | Остаются, переводятся на новое ядро с прежним поведением (включая удаление объекта при `/permremove` — привычка админов) |
