# GRM Faction Positions v5 — ранги и должности

Концепция. Код не написан, ничего не сломано. Документ для решения владельца.

---

## 1. Что не так сейчас

### 1.1. Ранг и должность — одно и то же поле

У участника ровно одно поле власти:

```
member = { Role = "Сержант", Department = "patrol", Subdepartment = "" }
```

`f.Roles` — плоский список без иерархии. Из-за этого нельзя выразить простые
вещи, которые нужны любой организации:

- «Сержант» — это **звание**, а «Командир отделения» — **должность**. Сейчас
  либо одно, либо другое, третьего поля нет.
- Два сержанта: один начальник патрульного отдела, второй рядовой патрульный.
  Система считает их **одинаковыми** — одни модели, одни права, один доступ.
- Чтобы сделать начальника, приходится плодить ранги: «Сержант», «Сержант —
  нач. отдела», «Сержант — зам». Список рангов распухает, а порядок подчинения
  всё равно нигде не записан.

### 1.2. Нет вертикали подчинения

- `f.Leader` — **один** на всю организацию.
- У подотдела есть поле `head`, но оно **пустое и нигде не читается** — заготовка,
  которую так и не подключили.
- У отдела начальника нет вообще.
- Кто кому подчиняется — нигде не хранится. Заместителя выразить нечем.

### 1.3. Права выдаются только рангу

`GRM.FactionPerms` хранит `roles[рангName] = { право = true }`. Следствие:
право «распоряжаться автопарком» получают **все** сержанты организации, а не
начальник транспортного отдела. Отделить нельзя.

### 1.4. Штат не считается

Квота (`quota`) есть **только у подотдела**. Нельзя сказать «начальник отдела —
1 место», «инспектор — 6 мест». Штатного расписания нет, вакансии не видны.

### 1.5. Найденный баг: два разных приоритета моделей

Порядок выбора формы **отличается в двух местах**:

| Где | Порядок |
|---|---|
| `sh_faction_fixes.lua` → `GetModelsForPlayer` (реальная выдача в мир) | подотдел → отдел → **ранг** → организация |
| `sh_grm_character.lua` → `modelsForContext` (превью в меню персонажа) | **ранг** → отдел → организация, **подотдел не учитывается вообще** |

То есть игрок в меню персонажа видит один список моделей, а в мир его одевают
по другому. Для сотрудника подотдела превью просто не показывает его форму.
Это чинится в рамках v5 сведением к одной функции.

## 2. Идея: три независимые оси вместо одной

| Ось | Отвечает на вопрос | Пример |
|---|---|---|
| **Ранг** (есть сейчас) | Какое у человека звание, выслуга | Рядовой, Сержант, Лейтенант |
| **Должность** (новое) | Какое место в штате он занимает и что ему можно | Начальник отдела, Заместитель, Инспектор |
| **Узел структуры** (есть сейчас) | Где он служит | Организация → Отдел → Подотдел |

Ключ в том, что оси **независимы**. Лейтенант может быть рядовым инспектором,
а сержант — начальником отдела. Именно это сейчас невозможно.

### Запись участника

```
member = {
    Role         = "sergeant",      -- ранг, как и раньше
    Department   = "patrol",
    Subdepartment = "",
    Position     = "patrol_head",   -- НОВОЕ: ключ должности
}
```

`Position` пустой = всё работает ровно как сегодня. Это основа обратной
совместимости: старые организации не ломаются и не требуют переделки.

### Запись должности

Должность живёт внутри организации и **прикреплена к узлу структуры**:

```
f.Positions = {
    patrol_head = {
        id     = "patrol_head",
        name   = "Начальник патрульного отдела",
        node   = "dept:patrol",   -- организация / отдел / подотдел
        kind   = "head",          -- head | deputy | senior | staff
        rank   = { min = "sergeant" },  -- минимальное звание (необязательно)
        slots  = 1,               -- штат: сколько мест
        perms  = { fleet_manage = true },
        tag    = "НАЧ. ПАТР",
    },
}
```

### `kind` — вот здесь и появляются «начальник, зам и т.д.»

| kind | Смысл | Вес власти |
|---|---|---|
| `head` | Начальник узла | 80 |
| `deputy` | Заместитель начальника | 60 |
| `senior` | Старший сотрудник, командир смены | 40 |
| `staff` | Рядовой сотрудник | 10 |

Вес — не ручное число, а следствие вида должности: меньше полей, меньше шансов
намудрить. Из веса **автоматически** выводится:

- кто в узле главный (наибольший вес);
- кто кем командует (сравнение весов в пределах узла и вверх по дереву);
- кто замещает начальника, когда его нет в сети (`deputy` узла);
- лидер организации = `head` корневого узла — то есть нынешний `f.Leader`
  становится частным случаем общего правила, а не отдельной сущностью.

Порядок подчинения перестаёт быть на словах и становится данными, которые
могут читать все модули.

## 3. Как это ложится на существующие модули

### 3.1. Права (`sh_grm_faction_perms.lua`)

Сейчас источник один — ранг. Станет три, складываются по ИЛИ:

1. право ранга (как сейчас, ничего не ломается);
2. право должности (новое);
3. персональный грант (уже есть в `GRM.Access`).

Плюс необязательный флаг у узла: **начальник наследует права подчинённых
должностей своего узла**. По умолчанию выключен — чтобы не раздать лишнего молча.

Важно: `GRM.Access` уже умеет спрашивать права организации через провайдер
`grm_faction_perms` с правилом имени `plates.issue` ↔ `plates_issue`. Достаточно
расширить **один** этот провайдер — и должности сразу заработают во **всех**
модулях, которые ходят через `GRM.Access.Can`: двери, CCTV, розыск, автопарк,
номера, телефония, медицина, пожарные. Переписывать их не нужно.

### 3.2. Модели и `models_admin`

Единый порядок, объявленный в **одной** функции `GRM.Factions.ResolveLoadout`,
которую зовут и выдача в мир, и превью в меню персонажа (лечит баг 1.5):

```
должность → подотдел → отдел → ранг → организация → общие
```

Должность — самая точная, поэтому она первая. Это позволяет то, чего сейчас нет:
у начальника отдела **своя форма**, отличная от формы его подчинённых в том же
отделе.

В `models_admin` дерево получает четвёртый уровень:

```
Организация
├── Общие модели организации
├── Ранги
│   └── Сержант
├── Отдел: Патрульная служба
│   ├── Модели отдела
│   └── Должности                 ← новый уровень
│       ├── Начальник отдела
│       └── Инспектор
└── Подотдел: Дорожный надзор
```

### 3.3. Редактор бодигрупп (`/bodygroups_admin`, сделан вчера)

Модуль уже построен на разрешении правил по цепочке областей, поэтому
расширяется без слома. Сейчас ключ правила:

```
модель | организация | отдел-или-подотдел | ранг
```

Станет:

```
модель | организация | узел | ранг | должность
```

Цепочка приоритета удлиняется: правило **должности** — самое сильное, сильнее
правила ранга. Прямо ваш случай: у начальника отдела нашивка на месте, у
рядового патрульного та же строка скрыта.

Совместимость: правила старого формата (4 поля) читаются как есть — при чтении
им дописывается пустая пятая часть. Уже настроенные правила **не пропадают**.

### 3.4. Меню персонажа

Меняется мало, потому что вчерашняя работа уже подготовила почву — в меню
уходит контекст `организация / отдел / подотдел / должность`. Добавляется одно
поле `position`, и правила бодигрупп начинают учитывать должность. Плюс
исчезает расхождение превью и реальной выдачи из п. 1.5.

### 3.5. Кадры, точки спавна, чат

- **Кадровое дело** (`sh_grm_faction_personnel.lua`): в историю пишется
  «назначен на должность», «снят с должности», «назначен и.о.». Сейчас там
  только ранг и отдел.
- **Точки спавна**: появляется `PositionSpawnPoints` — начальник может
  появляться в своём кабинете, а не в общей раздевалке.
- **Тег в служебном канале**: `GRM.Factions.ChannelTag` уже клеит теги
  организации, отдела и подотдела. Добавляется тег должности — в эфире сразу
  видно, что говорит начальник, а не рядовой.

### 3.6. Штатное расписание и вакансии

`slots` у должности даёт то, чего не хватало:

- «Начальник — 1 место, занято 1 из 1» — второго начальника система просто
  не даст назначить;
- свободные места = вакансии, они уже отображаются на бирже в админ-хабе;
- в реестре организации видно укомплектованность отделов.

## 4. Совместимость и порядок работ

Принципиально: **ни одна из фаз не ломает работающий сервер**. Организация без
должностей продолжает жить на рангах.

| Фаза | Что делается | Риск |
|---|---|---|
| **1. Данные** | `f.Positions`, `member.Position`, миграция (ничего не создаёт, просто добавляет пустые поля), `GRM.Factions.ResolveLoadout` + **починка бага 1.5** | низкий |
| **2. Управление** | Раздел «Должности» в `/factions`: создать, назначить, снять, штат, `kind` | низкий |
| **3. Права** | Расширение провайдера `grm_faction_perms` — должности начинают работать во всех модулях сразу | средний |
| **4. Внешний вид** | `models_admin` + `/bodygroups_admin` получают уровень должностей | средний |
| **5. Обвязка** | Кадры, точки спавна, теги в эфире, вакансии | низкий |

Каждая фаза — отдельный коммит со своим сим-стендом, как обычно.

## 5. Что это даёт на практике

Пример патрульной службы после внедрения:

| Человек | Ранг | Должность | Что получает |
|---|---|---|---|
| Иванов | Лейтенант | Начальник отдела | своя форма с нашивкой, право на автопарк и кадры, спавн в кабинете, тег «НАЧ. ПАТР» |
| Петров | Сержант | Заместитель | форма с нашивкой зама, права начальника когда тот не в сети |
| Сидоров | Сержант | Инспектор | обычная форма, нашивка скрыта, базовые права |
| Козлов | Рядовой | Инспектор | та же должность, что у Сидорова, но звание ниже — видно в реестре и в эфире |

Сейчас Петров, Сидоров и Козлов при одинаковом ранге неразличимы для системы,
а Иванова пришлось бы делать отдельным рангом.

## 6. Развилки, которые нужно решить до кода

1. **Ранги — общие для организации или свои у каждого отдела?**
   Общие проще и ближе к жизни (звание не меняется при переводе). Свои гибче,
   но сложнее в управлении и переводе людей.

2. **Наследование прав начальником — по умолчанию вкл или выкл?**
   Выключено безопаснее (ничего не раздаётся молча), включено удобнее.

3. **Автозамещение:** должен ли `deputy` автоматически получать права
   начальника, когда тот не в сети, или назначение и.о. делается вручную?

4. **Жёсткость штата:** запрещать назначение сверх `slots` совсем или
   разрешать с предупреждением?
