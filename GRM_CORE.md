# GRM Core — общие контракты платформы

**Версия:** 1.0.0
**Дата:** 16.08.2026
**Статус:** фундамент введён; старые системы переводятся на него постепенно, без слома публичных API и форматов данных.

## 1. Зачем нужен Core

GRM больше не должен решать доступ, сохранение, защиту net-запросов, аудит и перевод текста заново в каждом модуле. Core задаёт единый язык взаимодействия систем. Доменные модули сохраняют собственную бизнес-логику и совместимость, но новые интеграции используют общие контракты.

Core не является новым gamemode и не забирает данные у Documents, Vendor, CCTV, RadioNet или Perm. Он предоставляет реестры, безопасные операции и фасады над существующими владельцами данных.

## 3. Неподвижные правила

1. **RP-состояние принадлежит персонажу.** Ключ — `SteamID64:charN` через `GRM.Identity.CharacterKey`.
2. **Аккаунт используется только для авторизации, администрирования и аудита.**
3. **Клиент отправляет намерение, а не результат.** Сервер повторно определяет игрока, объект, дистанцию, право и допустимые значения.
4. **Каждый C→S receiver получает guard.** Минимум: частота и размер; для мирового объекта — дистанция; для действия — capability.
5. **JSON имеет версию.** Чтение SID-подобных ключей — `util.JSONToTable(raw, false, true)`.
6. **Повреждённый JSON не перезаписывается.** Сначала создаётся карантинная копия.
7. **`file.Write` не подтверждает успех.** Сохранение считается успешным только после read-back и повторного decode.
8. **Один класс — один владелец persistence.** Общий реестр маршрутизирует операцию, но не создаёт вторую запись.
9. **Деньги меняются только через Economy/Ledger API.**
10. **Составные изменения инвентаря будут выполняться только транзакцией.** До появления Transaction запрещено добавлять новые многошаговые перемещения.
11. **Мутация значимого RP-состояния пишется в `GRM.Audit`.**
12. **Окно имеет стабильный singleton key через `GRM.UI.Track`.** Callback очищает/проверяет panel до синхронного rebuild.
13. **Внутренние таблицы другого домена не являются API.** Используются публичная функция, capability, adapter или domain hook.
14. **Стабильные ID не переводятся.** Переводятся только подписи для человека.

Эти значения также доступны через `GRM.Core.Rule(id)` и нужны будущему статическому аудиту.

## 4. Общий язык идентификаторов

Все машинные ID пишутся в нижнем регистре на английском:

- capability: `domain.resource.action`, например `medical.patient.edit`;
- audit action: `resource.action`, например `patient.card.save`;
- net guard key: `domain.resource.action`;
- translation key: `domain.section.name`;
- hook: `GRM_<Domain><PastTense>`, если это публичный legacy-hook;
- backend: короткое имя владельца данных — `perm`, `vendor`, `cctv`, `radionet`.

Русские названия фракций, рангов и документов являются данными сервера, а не ID программного контракта.

## 5. Языки и локализация

Базовые языки: `ru` (по умолчанию) и `en`. Пользователь выбирает язык клиентской переменной:

```text
grm_language ru
grm_language en
```

Основные вызовы:

- `GRM.Lang.Register("ru", dictionary)` — расширить словарь;
- `GRM.Lang.Get(key, vars, locale)` — получить строку явно;
- `GRM.Lang.T(player, key, vars)` — выбрать язык игрока;
- `{name}` — безопасная подстановка параметра.

Правила локализации:

1. Серверная логика никогда не сравнивает переведённую строку.
2. Net-протокол передаёт ID и данные, клиент переводит подпись.
3. Отсутствующий перевод показывает стабильный key, поэтому дефект виден сразу.
4. Словарь домена регистрируется рядом с доменом; Core содержит только общие сообщения.
5. Русский остаётся fallback, чтобы существующий интерфейс не менялся внезапно.
6. Roboto регистрируется с `extended = true` для кириллицы.

## 6. Access

Capability регистрируется один раз через `GRM.Access.Register`. Проверка выполняется только сервером:

- `GRM.Access.Check(ply, capability, context)` возвращает `allowed, source`;
- `GRM.Access.Can(...)` — совместимый alias;
- `GRM.Access.List()` — каталог для будущего общего меню прав.

Типы назначения: `everyone`, `faction`, `role`, `department`, `account`, `character`. Приоритет — от общего к конкретному. Запрет равного приоритета сильнее разрешения. Персональный запрет персонажа сильнее разрешения фракции.

Единый файл назначений: `data/grm_core/access_grants.json`, схема-массив. Старые AccessManager пока остаются legacy-provider: если в Core нет явного назначения, решение принимает прежняя система. Благодаря этому миграция не меняет текущие права.

Общий редактор открывается командами `/grm_access`, `/доступы` или `grm_access`. Это крупное singleton-окно с каталогом capability, фильтром, списком назначений и формой для `everyone/faction/role/department/account/character`. Разрешение и запрет отображаются отдельно; все изменения отправляются одной защищённой операцией и записываются в аудит. Команда поддерживает обычный чат и EasyChat (`PlayerSayTransform` + `SkipPlayerSay`).

Первая группа capability:

- `medical.computer.use`, `medical.patient.edit`;
- `wanted.civil.view`, `wanted.civil.edit`;
- `fire.dispatch`, `fire.fight`;
- `cctv.view`, `cctv.configure`;
- `phone.equipment.use`;
- `world.perm.manage`;
- `doc.passport.issue`, `doc.weapon_license.issue`.

## 7. Persistence

`GRM.Persistence.LoadJSON` и `SaveJSON` реализуют общий безопасный цикл: version → decode без преобразования ключей → normalize/migrate → quarantine → write → exact read-back → verify decode.

Backend регистрирует `OwnsClass` либо `Owns`, затем поддерживаемые операции `Save`, `Remove`, `Reload`, `Inspect`. `Resolve` выбирает backend с максимальным priority. Конфликт не скрывается: запускается `GRM_PersistenceConflict` и пишется в аудит.

Зарегистрированы владельцы:

- `vendor` — собственная база торговцев;
- `cctv` — `GRM.CCTV.SavePermanent`;
- `radionet` — `GRM.RadioNet.PersistAdd/Remove`;
- `perm` — центральная база разворачиваемых объектов.

`/perminfo` показывает backend. Это позволяет администратору понимать, где реально хранится объект, и не создавать двойной перм.

## 8. Net Guard

`GRM.Net.Guard(ply, key, options, context)` поддерживает:

- token-bucket через `rate` и `burst`;
- максимальный `maxBits` из аргумента receiver;
- `requireEntity` и `distance` до `NearestPoint`;
- `capability` через `GRM.Access`;
- дополнительный серверный `permission` callback.

Guard вызывается до чтения и применения полезной нагрузки. `GRM.Net.String` и `GRM.Net.Number` нормализуют пользовательские значения. Неудачная проверка всегда fail-closed.

Первой мигрирована медицинская карта: сохранение и выдача физического бланка теперь имеют rate/size/capability guard. Ранее эти два receiver доверяли самому факту net-вызова после открытия компьютера. Административные receiver настройки Fire, Wanted, CCTV и Phone также получили общий rate/size/permission guard и аудит сохранений; их старые окна продолжают работать.

## 9. Audit

`GRM.Audit.Write(domain, action, actor, target, details)` пишет одну JSON-строку в:

```text
data/grm_core/audit/YYYY-MM-DD.jsonl
```

Actor содержит AccountKey, CharacterKey и RP-имя. Target хранит идентификатор объекта операции. Details ограничены по глубине, количеству полей и длине строк, чтобы журнал нельзя было раздуть произвольной таблицей.

Уже журналируются изменения медицинской карты, выдача физической медкарты и конфликты persistence-backend. Audit не заменяет доменные журналы мгновенно; на переходном этапе они могут существовать параллельно.

## 10. Порядок миграции старого модуля

1. Описать стабильные capability и audit action.
2. Зарегистрировать legacy callback без изменения старого UI.
3. Перевести серверные проверки на `GRM.Access` с legacy fallback.
4. Обернуть C→S receiver в `GRM.Net.Guard`.
5. Направить мутации в `GRM.Audit`.
6. Если модуль владеет мировыми entity — зарегистрировать persistence adapter.
7. Добавить словари, но не менять машинные ID.
8. Добавить sim-тест на allow/deny, rate/size и совместимость.
9. Только после этого удалять локальный access/persistence код отдельной миграцией данных.

## 11. Запрещённые обходы

- новый `*_access.json` вне общего Access без обоснованного доменного исключения;
- прямой `SteamID64` как ключ RP-записи;
- `util.JSONToTable(raw)` для SID/CharacterKey данных;
- сохранение поверх битого файла;
- два backend для одного класса;
- C→S receiver, который доверяет entity/index/цене/праву клиента;
- переводимые строки в качестве capability, enum или ключа JSON;
- прямое изменение чужой внутренней таблицы;
- новое окно без singleton lifecycle;
- молчаливый fallback при ошибке транзакции или сохранения.

## 12. Совместимость

Глобальные контракты `Factions`, `OpenAdminMenu`, `OpenLeaderMenu`, `refreshAllUI` сохраняются. Старые `Can*` API и собственные форматы Vendor/CCTV/RadioNet остаются рабочими. Core вводится как слой совместимости и постепенной консолидации, а не как одномоментная перепись платформы.

## GRM.Boot — приоритетная загрузка (v1.0.0)

Модуль `sh_00_grm_boot.lua` загружается первым и даёт всей сборке общий
планировщик старта. Без него всё «просыпалось» одновременно: 42 хука
`InitPostEntity` и больше сотни `timer.Simple` в первые секунды после карты —
чтение десятков JSON, спавн entity, сканы карты в несколько тиков.

**Приоритеты (tier):**

| tier | когда выполняется | что кладём |
|---|---|---|
| `critical` | немедленно при старте | ядро, без которого не работает ничего |
| `early` | первым в очереди | то, что обязано быть готово ДО входа игроков: двери, перм-энтити, точки спавна |
| `normal` | следом | обычная игровая логика: экономика, телефония, сигнализация, CCTV |
| `late` | в последнюю очередь | журналы, каталоги, чистки, топологии |
| `idle` | **никогда сам** | только по требованию: меню, редкие подсистемы |

**API:**

```
GRM.Boot.Task(id, tier, fn[, opts])    -- задача в очередь; opts.needs = { "другой.id" }
GRM.Boot.Lazy(id, fn[, opts])          -- задача только «по требованию»
GRM.Boot.Ensure(id[, причина])         -- выполнить сейчас (повторно — бесплатно)
GRM.Boot.Done(id)                      -- выполнена ли
GRM.Boot.Reset(id)                     -- пометить «выполнить снова» (после PostCleanupMap)
GRM.Boot.When(id, checkFn, fn[, opts]) -- «если условие есть — делаем, иначе ждём»
GRM.Boot.OnChat(команды, id)           -- чат-команда поднимает подсистему
GRM.Boot.OnUseClass(class, id)         -- использование entity поднимает подсистему
GRM.Boot.OnFirstPlayer(id)             -- первый вошедший игрок (на пустом сервере — никогда)
GRM.Boot.Defer(fn[, tier])             -- разовое отложенное действие
GRM.Boot.Status()                      -- отчёт; консоль: grm_boot_status
```

**Правила:**

* Очередь выполняется порциями с бюджетом `grm_boot_budget_ms` (по умолчанию
  2 мс на сервере, 3 мс на клиенте) — стартовая работа размазывается по тикам,
  а не встаёт пиком в один кадр.
* Задача с `needs` ждёт зависимости, даже если её приоритет выше.
* Падение одной задачи не ломает очередь (каждая под `pcall`, ошибка в лог).
* Любой новый тяжёлый старт оформляем задачей, а не своим `timer.Simple`.
* Всё, что нужно только по действию игрока, оформляем `Lazy` + триггер.
