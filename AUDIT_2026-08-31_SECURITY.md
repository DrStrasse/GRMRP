# Аудит безопасности и устойчивости GRM — 31.08.2026

Срез: коммит `840ae7e`, ветка `arena/01a03830-drstrasse`.
Объём: **568 файлов Lua** (без EasyChat), **357 серверных обработчиков
`net.Receive`**, 262 зарегистрированных net-сообщения, 348 консольных
команд.

Метод: не выборочное чтение, а сплошной автоматический разбор всех
серверных точек входа с последующей **ручной проверкой каждой находки**.
Первый прогон дал 158 «дыр»; после уточнения детектора (он не видел
вспомогательные функции вроде `inRange`, `rateOK`, `AD.Can`) осталось 98
кандидатов, из них по риску записи на диск — 2, и оба при чтении кода
оказались защищены. Ниже только то, что подтверждено глазами.

Инструмент разбора сохранён: `tools/audit_net_guards.py`. Его вывод —
список для чтения, а не приговор: доля ложных срабатываний высока
по построению, и это осознанный выбор в пользу «лучше лишнее покажет».

## 2. Подтверждённые проблемы

### 2.1. Телефоны исчезают при повреждении файла — ВЫСОКИЙ ✅ ИСПРАВЛЕНО `629c306`

`lua/autorun/server/sv_grm_phone.lua:818-824`

```
if not file.Exists(savePath(), "DATA") then return end
-- сначала СНОСИМ все телефоны с карты
for _, class in ipairs({...}) do
    for _, ent in ipairs(ents.FindByClass(class)) do ent:Remove() end
end
-- и только потом читаем файл
local data = util.JSONToTable(file.Read(savePath(), "DATA") or "") or {}
```

Порядок операций опасен: энтити удаляются **до** разбора файла. Если
JSON повреждён (обрыв записи при падении сервера, полный диск), разбор
вернёт `nil`, а телефоны уже снесены. Вся телефонная сеть карты
исчезает без следа и без сообщения в консоль.

Это единственный загрузчик в проекте, где `util.JSONToTable` вызван
**без `pcall`** — остальные 11 обёрнуты. Здесь же ещё и нет карантина
битого файла, который есть в валюте, экономике и документах.

**Что делать:** сначала прочитать и проверить данные, и только при
успешном разборе сносить старое. Битый файл — в карантин, как уже
сделано в `sh_grm_currency`.

### 2.2. Фотоальбом не ограничен по серверу в целом — СРЕДНИЙ

`lua/autorun/sh_grm_photo.lua:12`

```
P.Config = { MaxBytes = 12000, MaxPerPlayer = 12, MaxMail = 24 }
```

Лимиты **на игрока** есть (12 КБ × 12 = 140 КБ), общего лимита на сервер
нет. Файлы `.jpg` пишутся в `data/` и никогда не удаляются — записи
остаются и после ухода игрока. За полгода работы с активной аудиторией
это десятки тысяч файлов в одном каталоге.

Прямой угрозы нет: злоупотребить трудно из-за кулдауна. Но диск
заполняется молча и необратимо.

**Что делать:** чистка снимков игроков, не заходивших N дней, плюс
потолок на общее число файлов.

### 2.3. 116 модулей пишут файлы напрямую — СРЕДНИЙ

`file.Write` встречается **207 раз в 116 файлах**, и лишь около **48**
вызовов сопровождаются проверкой чтением (read-back). Централизованной
очереди записи нет: `GRM.Save` существует, но им пользуется меньшинство.

Следствия:
- при падении сервера в момент записи файл остаётся обрезанным, и модуль
  без read-back об этом не узнает;
- одновременная запись десятка модулей даёт всплеск дисковых операций —
  один из вероятных источников микрофризов;
- у каждого модуля свой формат карантина, часть не делает его вовсе.

**Что делать:** это не переписывание всего разом. Достаточно перевести
на общую очередь модули, которые пишут часто (валюта, инвентарь,
документы, фракции), — остальные трогать не обязательно.

## 3. Слабые места конструкции

Не уязвимости прямо сейчас, но места, где ошибка одного разработчика
сразу создаёт дыру.

### 3.1. Защита обработчиков держится на дисциплине ✅ ЗАКРЫТО СТОРОЖЕМ `629c306`

Из 357 серверных `net.Receive` через общий `GRM.Net.Guard` проходят
только **53**. Остальные защищаются вручную и по-разному: где-то
`IsSuperAdmin`, где-то локальные `inRange`/`rateOK`, где-то проверка
владельца.

Сейчас это работает — я проверил критичные вручную. Но новый обработчик,
написанный без единого правила, легко окажется голым, и заметить это
можно только чтением кода.

**Что делать:** не переписывать 300 мест, а закрыть будущее — стенд,
который падает, если в новом серверном `net.Receive` нет ни одного
признака валидации. Такой сторож уже работает для чистоты имён
(`sim_global_hygiene`) и конфликтов хуков.

### 3.2. `TakeMoney` списывает частично и сообщает об ошибке

`sh_grm_currency.lua:542`

```
local taken = math.min(amount, rec.balance)
rec.balance = rec.balance - taken
...
return taken >= amount
```

Если денег не хватает, функция забирает **сколько есть** и возвращает
`false`. Вызывающий код, который проверяет результат, откажет в
операции — но деньги у игрока уже списаны.

Результат `TakeMoney` игнорируется в **22 местах**. Прямой утечки я не
нашёл (везде выше стоит проверка баланса), но конструкция опасна: любой
новый вызов без предварительной проверки съест деньги игрока молча.

**Что делать:** либо списывать «всё или ничего», либо переименовать в
`TakePartial`, чтобы поведение было очевидно из названия.

### 3.3. 524 чтения строк от клиента без явной обрезки

`net.ReadString()` без `string.sub` рядом. Большинство попадает в
безопасные места, но длинная строка в NW-переменной или в 3D2D — это
нагрузка на сеть и потенциальный разрыв у клиентов.

Проверенные точки (описание маски, названия дверей, подписи фото)
обрезаны корректно. Это не находка, а зона риска для новых правок.
