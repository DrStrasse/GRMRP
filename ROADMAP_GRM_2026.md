# GRM — архитектурный аудит и концепция дальнейшего развития

**Дата:** 16.08.2026  
**База:** `arena/01a00b1f-drstrasse`, HEAD `849ca45`  
**Объём:** 450 Lua-файлов, ~133 700 строк, 67 entity, 9 SWEP-каталогов, 20 stool, 90 sim-стендов.

---

## 1. Итоговый вывод

GRM уже является не набором отдельных аддонов, а самостоятельной RP-платформой поверх Sandbox. В ней сформированы четыре крупных контура:

1. **Персонаж и общество:** CharacterKey, внешность, фракции, служба, документы, образование, медицина, инвентарь.
2. **Государство:** экономика, казна, услуги, лицензии, полиция, жандармерия, спецслужбы, суд, розыск, штрафы, арест.
3. **Мир и имущество:** двери, перм, PropProtect, транспорт, дилер, багажник, торговцы, производство, шахта, кухня.
4. **Оперативные службы:** пожарная система, 911, сигнализация, CCTV, телефония, радиосеть, вещание, прослушка.

Главное достоинство проекта — системы уже связаны игровыми потоками, а не существуют изолированно. Лицензия проверяется оружейником, работа резервирует казну, лечение пишет медкарту, труп хранит физические документы, служба меняет форму и доступ к подработке.

Главная проблема — рост происходил вертикальными монолитами и локальными менеджерами доступа. Сейчас следующий крупный функционал опаснее добавлять «ещё одним sh_grm_*.lua»: сначала нужны единые базовые контракты и наблюдаемость.

**Рекомендация:** не переписывать сборку целиком. Провести последовательную консолидацию ядра, сохраняя публичные API и миграции данных.

## 4. Сильные стороны

1. **CharacterKey принят как архитектурный закон.** Это фундамент для нескольких персонажей на аккаунт.
2. **Серверная авторитетность.** Большинство новых модулей перепроверяют права, дистанцию и данные.
3. **Физические RP-циклы.** Деньги, документы, трупы, руда, товар, багажник существуют в мире.
4. **Большая тестовая база.** 90 стендов — необычно сильный актив для GLua-проекта.
5. **Совместимость и миграции.** Старые данные чаще импортируются, а не отбрасываются.
6. **Общая визуальная идентичность.** Тёмный XUI/Roboto и 3D2D-таблички формируют цельный продукт.
7. **Системные интеграции.** Бюджеты, документы, лицензии, фракции и службы реально зависят друг от друга.

## 5. Главные архитектурные риски

### P0. Монолиты и глобальный порядок загрузки

Крупнейшие файлы: Documents ~4k, Factions ~3.5k, Faction Fixes ~3.1k, Economy ~3k, Q-menu ~2k. Ошибка в одном callback ломает целое ведомство. Порядок autorun используется как dependency injection.

**Решение:** оставить autorun-файл как loader/compat facade, а реализацию постепенно вынести в `lua/grm/<domain>/sh_*.lua`, `sv_*.lua`, `cl_*.lua`.

### P0. Много независимых менеджеров доступа

Доступы отдельно существуют у Documents, Medical, Wanted, Fire, Alarm, CCTV, Phone, Doors, Services, FactionPerms. Одной фракции приходится ставить галочки в нескольких окнах.

**Решение:** `GRM.Access` с capability IDs:

```text
doc.passport.issue
medical.computer.use
medical.patient.edit
wanted.civil.edit
fire.dispatch
fire.fight
world.perm.manage
```

Старые `Can*` остаются адаптерами.

### P0. Несколько систем персистентности мира

Perm, Vendor, CCTV, RadioNet, Logistics, Fire и дилер сохраняются отдельно. Это допустимо, но пользователь ожидает единое поведение `/permadd`.

**Решение:** реестр persistence adapters:

```lua
GRM.Persistence.Register("vendor", {
  OwnsClass = function(class) ... end,
  Save = ..., Remove = ..., Reload = ..., Inspect = ...
})
```

`/permadd` становится единым фасадом и сообщает, какой backend использован.

### P0. Net-поверхность

Сотни каналов и receivers сложно проверить вручную. Основные риски: отсутствующий rate-limit, полный дамп таблиц, несовпадение сигнатур, дубли receiver одного имени.

**Решение:** восстановить/создать `tools/proto_audit.py`; добавить manifest направления и payload; CI запрещает неизвестный receiver и C→S без guard.

### P1. UI-фрагментация

373 регистрации шрифтов, десятки локальных палитр и helper-кнопок. Встречаются абсолютные размеры, ранний `GetWide()==0`, NULL Panel после rebuild.

**Решение:** расширить `GRM.UI` до набора компонентов: Frame, Tabs, Scroll, Card, Button, FormRow, CharacterPicker, DocumentBlank. Один lifecycle/singleton.

### P1. Данные и транзакции

Деньги уже защищены хорошо, но инвентарь/контейнеры используют несколько последовательных мутаций. При сбое между «удалить» и «добавить» возможна потеря/дублирование.

**Решение:** `GRM.Inventory.Transaction`: reserve → validate → commit/rollback. Использовать для трупа, багажника, торговца, склада, документов.

### P1. Тесты часто статические

Стенды прекрасно ловят контракты и прошлые ошибки, но часть проверяет наличие строк. Они не заменяют реальный dedicated-server smoke test с двумя клиентами.

**Решение:** три уровня:
1. static contract;
2. LuaJIT state simulation;
3. GMod integration smoke на тестовой карте.

### P2. Производительность

720 hooks и 126 timers не означают проблему сами по себе, но несколько Think проходят `player.GetAll`/`ents.FindByClass` регулярно. С ростом онлайна это станет заметно.

**Решение:** центральный scheduler с частотами 0.1/0.5/1/5/10 сек, профилирование длительности hook и бюджет сетевого трафика.

## 6. Целевая архитектура GRM Core

```text
GRM.Core
 ├─ Identity      AccountKey / CharacterKey / Actor snapshot
 ├─ Access        capabilities + faction/role/department/character grants
 ├─ Persistence   JSON schema/version/quarantine/read-back/adapters
 ├─ Net           rate-limit, distance, payload validation, pagination
 ├─ Audit         unified append-only journal
 ├─ UI            components + singleton lifecycle + theme
 ├─ Spatial       safe positions, markers, districts, routes
 ├─ Inventory     instance items + transactions + containers
 └─ Events        typed domain hooks / incident bus
```

Доменные модули не читают чужие внутренние таблицы напрямую. Они используют API и события.

Пример:

```text
911 Revived
 → Medical.AddEncounter
 → Economy.Transfer(state → hospital)
 → Achievements.Note
 → Incident.CloseStage
 → Audit.Write
```

## 7. Концепции дальнейшего развития

### 7.1. Incident/Dispatch Core

Объединить 911, Fire, Alarm и часть Wanted общей сущностью `Incident`:

```text
id, type, priority, position, district,
caller, subjects, assignedUnits,
stages, evidence, costs, opened, closed
```

Типы: medical, crime, fire, alarm, road, infrastructure. Каждая служба получает свой UI и права, но журнал/назначение/маркер едины.

**Польза:** один вызов может одновременно назначить медиков и полицию; пожар с пострадавшими не создаёт три несвязанных записи.

### 7.2. 911 v2 и медицина

- состояния: wounded → unstable → stabilized → transported → admitted → discharged/dead;
- носилки и погрузка в разрешённую скорую;
- зоны госпиталя/морга;
- лечение по типу травмы, а не одна кнопка revive;
- расход бинтов, крови, адреналина;
- автоматическая запись encounter в медкарту;
- труп: chain of custody, пакет улики, вскрытие, причина смерти;
- respawn только после смерти/морга по серверным правилам.

### 7.3. Investigations Core

Объединить дела спецслужбы, Wanted, тела 911, CCTV-фото и RoomTap:

- дело имеет участников, статьи, заметки, доказательства;
- доказательство имеет source, hash/id, collectedBy, collectedAt, custody history;
- фотография, документ, оружие, выписка звонка или осмотр тела прикрепляются одинаково;
- суд читает дело, но не внутренний журнал спецслужбы без допуска.

### 7.4. Documents v3 — документный кошелёк

- отдельный контейнер «кошелёк документов» на 8–12 бланков;
- физические копии остаются instance-items;
- команды/C-меню показывают только находящиеся при персонаже бланки;
- потеря/кража, заявление об утрате, перевыпуск;
- QR/serial verify без настоящего QR-рендера: номер + подпись реестра;
- физические дипломы и судебные решения;
- разные легенды прикрытия могут иметь индивидуальные обложки и уровень достоверности.

### 7.5. Factions v4 — организация и служба

- duty sessions: начало, конец, длительность, пост/машина;
- статусы roster: на службе, вне службы, выходной, отпуск, отстранён;
- расписание/лимит одновременного состава;
- журнал выдачи формы/оружия;
- `/members` и интерфейс используют один Roster API;
- лидерские полномочия как capabilities, а не специальный if.

### 7.6. Jobs v4

**Такси:**
- вызов живого пассажира через телефон;
- водитель принимает заказ;
- посадка проверяется по общей машине;
- такса: фикс + цена/дистанция, пределы администрации;
- оплата пассажиром, комиссия/субсидия казны;
- рейтинг водителя и отказ.

**Мусоровоз:**
- контейнеры имеют накопление отходов;
- маршрут зависит от заполнения;
- физический объём машины;
- сдача на свалке/переработке;
- муниципальный контракт из бюджета.

**Курьер:**
- физический пакет instance-item;
- отправитель/получатель;
- подпись доставки;
- риск кражи и страховка.

### 7.7. Economy v4 — ledger

Любая операция становится записью:

```text
txId, debitAccount, creditAccount, amount,
reason, actor, character, faction, timestamp, refs
```

Счета: cash, bank character, faction treasury, state treasury, escrow, vendor, service. Текущие API `GiveMoney`, `FactionBudgetAdd`, `StateBudgetAdd` становятся фасадами ledger.

**Польза:** невозможны деньги «из воздуха» без явно указанного системного счёта; проще расследовать дюпы.

### 7.8. Business/Vendor v3

- торговец принадлежит бизнесу/фракции;
- бизнес-лицензия гейтит работу;
- остатки товара, закупка и поставки;
- касса и выручка в счёт организации;
- оружейник проверяет лицензию покупателя и лицензию бизнеса;
- `/permadd` работает через persistence adapter;
- административный audit изменения цены/ассортимента.

### 7.9. World Objects v2

Объединить service tool, vendor tool, bank tool и perm tool вокруг `GRM.WorldObject`:

- placement preview/ghost;
- snap/grid;
- inspector;
- owner/persistence backend;
- undo before/after;
- список объектов карты;
- health/status diagnostics.

Взять паттерны MapStudio, но не переносить весь редактор.

### 7.10. Communications Core

Phone, RadioNet, Broadcast, Alarm и RoomTap должны использовать единый bus:

```text
channel, source, recipients, coverage,
quality, encrypted, interceptedBy, timestamp
```

Это даст единые основания прослушки, журнал связи, качество сигнала и аварийный приоритет.

### 7.11. Service Desktop

Не возвращать тяжёлую «полноценную ОС» как обязательный слой. Создать общий shell служебных компьютеров:

- единая шапка/логин/права;
- приложения как зарегистрированные панели;
- notifications/tasks;
- печать через общий Print Service;
- профиль конкретного ведомства.

Существующие `grm_comp_*` можно постепенно перевести без смены entity-классов.

## 10. Правила для всех новых систем

1. RP-состояние — только CharacterKey.
2. Клиент присылает намерение, сервер заново получает объект/персонажа/права.
3. C→S: rate-limit, distance, size clamp.
4. JSON: version, quarantine, read-back, массивы для SID-записей.
5. Деньги — только через экономический API/ledger.
6. Инвентарь — только транзакцией.
7. Окно — singleton через GRM.UI.
8. Никаких чужих `BuildCPanel` в собственном UI.
9. Новый hook/timer имеет lifecycle cleanup и документированную частоту.
10. Любая новая система: unit/sim, integration contract, migration test.
11. Публичный API и hooks документируются до интеграции соседа.
12. Один источник истины, остальные — кеши/проекции.

## 11. Что не рекомендуется

- Полный rewrite всей сборки одним коммитом.
- Ещё один независимый AccessManager.
- Ещё один собственный формат перма без adapter.
- Прямые изменения `GRM.Inventory` slots из доменного модуля без транзакции.
- Полные дампы registry клиенту.
- Частые `ents.FindByClass`/`player.GetAll` в каждом отдельном Think.
- UI на абсолютных размерах без теста 1280×720.
- Функциональность только через чат-команды без профильного UI/API.
- Автовосстановление предмета, если игрок осознанно его потерял/передал.

## 13. Финальная рекомендация

GRM стоит развивать как **RP operating platform**, а не коллекцию механик. Контента уже достаточно. Максимальную отдачу сейчас даст не четвёртый терминал или пятая профессия, а единые Access, Persistence, Net Guard, Audit, Inventory Transaction и Incident Core.

После этого новые системы — EMS, суд, бизнес, транспортные контракты — будут добавляться быстрее и перестанут повторять уже решённые проблемы с правами, пермом, окнами, net-пакетами и потерей данных.
