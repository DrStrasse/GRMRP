# GRM ADDON GUIDE — единое руководство по написанию аддонов и модулей

**Статус:** актуальное, единственное сводное руководство сборки.
**Дата:** 2026-09-01.
**Кому:** агенту при каждом новом модуле/аддоне/правке, владельцу — для проверки.
**Что внутри:** правила, выросшие из реальных багов живого сервера, аудитов,
стендов и прошлых сессий. Каждое правило имеет причину — это не вкусовщина.

---

## 0. Как пользоваться документом

1. **Новый модуль** → пройди сверху вниз: §1 (чеклист) → §2 (архитектура) →
   §3 (стиль) → §4 (рендер) → §5 (дублирование) → §6 (оптимизация) →
   §7 (сеть) → §8 (данные) → §9 (UI) → §10 (стенды) → §11 (запреты).
2. **Правка в большом модуле** → §3, §5, §6 + стенд по правилам §10.
3. **Непонятная ошибка** → §12 (справочник «симптом → причина → правило»).
4. **Ворота перед пушем**: §13 (инструменты), их вывод — обязателен.

## 1. Чеклист нового модуля (порядок обязателен)

1. Идея → **архитектурная схема**: где живёт (shared/server/client/entity),
   какие узлы, где хранится, кто владелец данных.
2. **Проверь дубли**: нет ли уже реализации (даже частичной) в другом файле
   — см. §5. Если есть — расширяем существующее, а не пишем второе.
3. Файлы по канону: `sh_имя.lua` — общая логика и API, `server/sv_имя.lua` —
   сервер, `client/cl_имя.lua` — клиент. Всё в `lua/autorun/` (SRV/CLI — в
   подкаталогах `server/`/`client/`).
4. Старт — только через `GRM.Boot` (§2.3). Никаких своих
   `InitPostEntity`/`timer.Simple` на старт.
5. Реализуй с правилами §3–§9.
6. **Стенд**: `tools/luatest/sim_<имя>.lua` — воспроизводит все баги ДО фикса.
7. **Откатная проверка стенда** (§10.2) — обязательно.
8. Синтаксис всех файлов `loadstring`/`loadfile`.
9. `python3 tools/lua_style.py --check`.
10. `python3 tools/audit_perf.py --gate` + `python3 tools/audit_net_guards.py`.
11. Полный прогон стендов — не хуже базы, без новых красных.
12. README.md / CHANGELOG.md / ARCHITECTURE.md (и этот файл, если добавилось
    правило) → `python3 tools/build_dist.py` → **commit + push сразу**.

## 2. Архитектура

### 2.1 Namespace и файлы

- Всё публичное — в таблице модуля: `GRM.Модуль.Функция`. Голых глобалов нет
  (кроме контрактных `Factions`, `OpenAdminMenu`, `OpenLeaderMenu`,
  `refreshAllUI` — их НЕ локализовать).
- Порядок загрузки `lua/autorun/` — **алфавитный**. Пользуемся осознанно:
  `sh_00_grm_ui.lua` первым, `zz_*` последними. Имя нового файла = часть
  контракта; переименование меняет порядок загрузки.
- Идентификаторы: capability `domain.resource.action`; net-guard key и
  audit action `resource.action`; hook `GRM_<Domain><PastTense>`; backend —
  короткое имя владельца (`perm`, `vendor`, `cctv`, `radionet`).
- CharacterKey = `SteamID64:charN` — **весь** RP-стат принадлежит персонажу.
  Аккаунт (`SteamID64`) — только auth/admin/audit.

### 2.2 Ядро — использовать, не изобретать

| Модуль | Файл | Что даёт |
|---|---|---|
| `GRM.UI` | `sh_00_grm_ui.lua` | singleton-жизненный цикл окон (`Track/Close/IsOpen`), `Utf8Sub` |
| `GRM.Core`, `GRM.Lang` | `sh_01_grm_core.lua` | правила (`GRM.Core.Rule`), переводы ru/en |
| `GRM.Persistence` | `sh_02_grm_persistence.lua` | JSON: версия→decode→normalize→карантин→запись→read-back→verify; реестр backend |
| `GRM.Access` | `sh_03_grm_access.lua` | capability registry |
| `GRM.Net` | `sh_04_grm_net.lua` | Guard (rate/burst/размер/дистанция/capability), Stream (чанки 8 КБ), String/Number |
| `GRM.Audit` | `sh_05_grm_audit.lua` | JSONL-журнал `data/grm_core/audit/YYYY-MM-DD.jsonl` |
| `GRM.Perf` | `sh_06_grm_performance.lua` | реестры entity (`Entities`), `Players`, `Throttle`, change-only NW (`NWString/NWInt/NWBool/NWFloat`), `Coalesce`, `Queue`, `Spread`, `Material`, `EyeTrace` |
| `GRM.Save` | `sh_07_grm_save.lua` | отложенная запись на диск: `Register` + `Mark` |
| `GRM.Boot` | `sh_00_grm_boot.lua` | планировщик старта по тирам |

### 2.3 Старт — `GRM.Boot`

Тиры: `critical` (ядро) → `early` (до входа игроков: двери, перм, спавнпоинты)
→ `normal` (игровая логика) → `late` (журналы, каталоги) → `idle` (только по
требованию). Очередь выполняется порциями с бюджетом `grm_boot_budget_ms`.

- `GRM.Boot.Task(id, tier, fn, opts)` — обычная задача; `opts.needs` — зависимости.
- `GRM.Boot.Lazy(id, fn, opts)` — только по требованию; триггеры:
  `OnChat`, `OnUseClass`, `OnFirstPlayer`, `When`, `Ensure`.
- Падение одной задачи не ломает очередь (всё под `pcall`).
- Диагностика: `grm_boot_status`.

**Запрещено:** свой `InitPostEntity`/`Initialize`-хук для старта подсистемы.

### 2.4 Сетевой слой

- Все имена — через `util.AddNetworkString` **на сервере**, иначе
  `net.Start` даст «unpooled message».
- Клиент шлёт **намерение**; сервер повторно определяет игрока, объект,
  дистанцию, право, допустимые значения.
- Каждый C→S receiver — через `GRM.Net.Guard` ДО чтения payload (fail-closed).
- Большие таблицы — `GRM.Net.Stream` (сжатие + куски по 8 КБ, ≤200 кусков);
  приём — честная сборка по индексам с дедупликацией и лимитами.
- Имена сообщений — в shared-константах, не хардкодить строки по обе стороны.

## 3. Стиль кода

### 3.1 Оформление

| Правило | Значение |
|---|---|
| Отступ | 4 пробела, без табов |
| Конец файла | ровно один перевод строки |
| Переводы строк | LF, без BOM |
| Хвостовые пробелы | нет |

Проверка: `python3 tools/lua_style.py --check` (исправление: `--fix`).
Не трогать формат стороннего кода (`lua/easychat/`) и литералы `[[...]]`.

### 3.2 Приватное/публичное

- Всё приватное — `local`. Всё публичное — в таблицу модуля.
- **Замыкание, вызывающее local-функцию ниже по файлу, требует
  форвард-декларации** `local X` выше. Иначе файл грузится, а в бою:
  `attempt to call global 'X' (a nil value)`. Проверка:
  `tools/luatest/sim_forward_locals.lua`.
- Глобальные имена без префикса (`ui`, `data`, `a`) — конфликт с чужими
  аддонами; префикс обязателен.

### 3.3 Комментарии

Комментарий объясняет **почему** (какой баг это предотвращает), на русском.
«Прибавляем единицу» над `count = count + 1` — мусор. Запрещено «упрощать»
код, убирая прокомментированную защиту.

## 4. Рендер — правила

> Главный источник «не видно/мерцает/чёрное/полоска» — неверный API или
> рендер в кадре того, что строится один раз (и наоборот).

### 4.1 Камеры и сцены

1. **`cam.Start3D(eye, ang, fov, x, y, w, h, near, far)`** — сигнатура
   (x, y, w, h), а НЕ (w, h, near, far). Ошибка даёт рендер «полоской».
   Всегда `0, 0, w, h`.
2. `cam.Start3D2D(ent, pos, ang, scale)` — 2D-поверхности мира; каждая
   поверхность — своя пара Start/End. Ошибка внутри `Paint`/`Draw`
   оставляет матрицу открытой → **оборачивать в `pcall`** либо
   гарантировать End в `end`-ветке.
3. Рисование интерфейса в мире — в `ENT:Draw`/`DrawTranslucent`
   (рисуется в 1-м проходе и не попадает в стены неправильно),
   а не в `Think`.
4. **Камера сцены** (CalcView-стиль): тело игрока двигать нельзя — ломается
   физика и рендер себя; методы позиции локального игрока на время кадра
   подменяются только там, где это допустимо (кат-сцены, вьюпорт студии —
   вьюпорт собственной `cam.Start3D` НЕ трогает игрока).

### 4.2 Render-to-texture / снимки

5. RT-экран: `render.PushRenderTarget/PopRenderTarget` или готовый GPU-паттерн
   (Wiremod): рисуем сцену в буфер → выводим текстурой. **`NeedsUpdate`** —
   перерисовывать RT только при изменении содержимого.
6. `render.Capture` — для кадров/снимков; ограничивать размер (у нас 480×320
   q78) и **сжимать перед net** (`util.Compress`, куски ≤8 КБ, ≤200 кусков).
7. `render.Clear` — только внутри собственного RT, не в мировом кадре.

### 4.3 Материалы, модели, свет

8. **`Material()` не в кадре.** Кэш по пути (таблица `<path> → mat`).
   То же для `surface.CreateFont` (создавать один раз при загрузке).
9. `DModelPanel` (клиент): `SetFOV` явный, `SetModel` + `SetAnimated(true)`,
   `LayoutEntity = function() end` если нужна статичная камера; модель
   проверять в каталоге ДО `SetModel` (иначе пустая панель).
10. `render.Model(mdl, pos, ang, scale, color)` — ок; **позиция/поворот
    из данных, не из `EyeAngles` на каждый кадр** (если это статичный объект).
11. `DynamicLight` — в `Think` с `DieTime`, не в Paint.
12. Ghost-превью (призрак при постановке): `cam.IgnoreZ(true)` +
    `SetBlend` + `SetColorModulation` + `DrawModel` + сброс.
13. Стекл/порталы: `SetStencilEnable` + `STENCIL_REPLACE`/`EQUAL` +
    ClientsideModel `SetNoDraw` + `EnableMatrix("RenderMultiply", ...)`.
14. **Тонировка и подложки**: полупрозрачная заливка всего экрана в
    `DPanel.Paint` окна затемняет 3D-сцену под ним (баг «чё за потемнение»).
    Подложку рисуем только в своей панели, не поверх мира.

### 4.4 Гизмо и 3D-редакторы

15. **Порядок осей — детерминированный, массивом, не `pairs()`** (случайный
    порядок = «беру один, вращает другой»).
16. Кольца вращения: отбор только **ближней** к камере половины; иначе
    обратная сторона перехватывает клики у соседней оси.
17. Маппинг осей: `Angle(p,q,r)` = roll→Forward(X), pitch→Right(Y),
    yaw→Up(Z). Маппинг «по алфавиту» x→pitch — баг «Z вращает по X».
18. Подсветка активной оси обязательна; наконечники — не проволочные шары.
19. Пик гизмо В КАДРЕ (Think), drag — с `MouseCapture(true)`, орбита — `MouseCapture`.
20. Матрицы сцены: `EnableMatrix("RenderMultiply", mat)` — недеструктивное
    масштабирование клиентских моделей; не трогать `SetModelScale` у
    общих сущностей без нужды.

### 4.5 Маркеры, HUD, ленты

21. Маркеры в мире предпочитать **экранным 2D** (`HUDPaint` +
    проекция `WorldToScreen`), если нужна видимость «сквозь стены» —
    `cam.IgnoreZ` только вокруг конкретного Draw-блока.
22. Ленты/провода/кривые — отрезками (`DrawBeam`/`DrawLine`) с ограниченным
    числом сегментов (у нас 128–384 на кадр, не больше); не рисовать
    физику-проводку каждый кадр при бездействии.
23. HUD: один реестр полос (`GRM.HUD.RegisterBar`), модули не рисуют своё
    поверх; чужие полосы звать через `pcall` (ошибка модуля не роняет HUD).
24. `surface.PlaySound` — звук «выстрелил и забыл»; для петли/фона —
    `EmitSound` с handle и остановкой (или SoundPatch), иначе не выключить.

## 5. Дублирование — правила

> Дублирование — самый дорогой класс багов: две копии живут в разных
> файлах, правят одну, вторая остаётся старой.

### 5.1 Обработчики

1. **Один владелец на одно имя**: `net.Receive` заменяет, `hook.Add` с тем
   же именем заменяет. Два «просто так» обработчика → работает один,
   какой — решает алфавит загрузки.
2. Допустимы: одно имя в SERVER и в CLIENT (разные машины); осознанная
   замена `hook.Remove` тем же именем сразу перед `hook.Add`; защита
   флагом (`if not X then ... end`).
3. Проверка: `tools/luatest/sim_net_hook_conflicts.lua`.

### 5.2 Один владелец данных

4. **Один класс — один backend persistence**. Общий реестр маршрутизирует,
    второй backend = двойные записи и конфликт (`GRM_PersistenceConflict`).
5. Один файл данных — один модуль-писатель. Примеры прошлых багов:
   двойная экономика (`GRM.FactionBudgetGet` в двух файлах + **два налоговых
   таймера = двойной налог**), телефон, сохранённый и магазином, и
   SaveMapEntities (решено флагом `GRMPhoneShopOwned`).
6. **Одна каноническая функция проверки** на сущность. «Является ли игрок
   лидером» было реализовано в 4+ файлах — консолидировать в `FactionsAPI`.
   Правило видимости (имя над головой, HUD трубы) — одна сервер+
   клиент-совместная функция.
7. Правило «что показывает HUD» не дублировать в подсказках/клиенте
   текстом — брать из той же функции.

### 5.4 Реестр вместо копий (правило «двух мест»)

12. **Если добавление нового вида сущности требует правок более чем в
    ДВУХ местах — сущность обязана стать таблицей-реестром**, а механика
    вокруг неё — общей. Оплачено дважды: оси иерархии фракции
    (роль/должность/отдел/подотдел) жили в шести местах каждая — находка
    157 (загрузчик поднимал не все оси, точки «пропадали») и ось v5
    «должность» (забыли ветку в `ClearSpawnPoints` — очистить нельзя).
13. Признак для ревью: **две подряд идущие ветки, различающиеся только
    именем поля и текстом сообщения**. Лестница `if x == "a" … elseif
    x == "b" …` по одной переменной — то же самое: таблица-диспетчер
    `HANDLERS[x]` вместо N сравнений (и один лукап вместо N на вызов).
14. Одна функция — один смысл на весь проект. `charKey` существовала в
    36 файлах в 25 редакциях: часть возвращала `""`, часть — голый
    `SteamID64` без слота. Канон — `GRM.CharKey` (ядро), модуль делает
    `local charKey = GRM.CharKey`.
15. Стенд на реестр пишется **циклом по всем видам**: один сценарий
    прогоняется для каждой строки реестра. Тогда «забыл место для нового
    вида» краснеет именно на нём (`sim_spawn_points.lua`, раздел 8).
16. Детектор: `python3 tools/audit_slop.py` — лестницы, клоны функций,
    окна копипасты, мёртвый код, аллокации в render-хуках, дубли
    `hook.Add`. Инструмент показывает, решение — за человеком.

### 5.3 UI без дублей

8. Окно — singleton через `GRM.UI.Track`; второй вызов открывает то же окно,
    а не создаёт второе. Один путь открытия: регистрация команды либо
    с клиента, либо с сервера (двойная регистрация = мерцание/пересоздание).
9. Не копировать логику из соседнего модуля «потому что похоже» —
   копия расходится. Общее — выносить в общий модуль (`GRM.*`).
10. Клиент не может жить без серверной функции: не звать с клиента
    `ServerSideOnly` API — гаснет молча. И наоборот: клиентская функция,
    которой нет в файле, — runtime-ошибка при вызове.
11. Каталог моделей/материалов/звуков — один список на модуль; пикеры
    читают его, а не свои копии.

## 6. Оптимизация — правила

> Микрофризы ≈ покадровые хуки + дисковые записи + большие синхронизации.

### 6.1 Покадровые хуки

1. В `Think`/`HUDPaint`/`PostDraw*`/`SetupMove`/`CalcView` **запрещены**:
   `ents.FindByClass`, `ents.GetAll`, `player.GetAll`, `util.Trace*`,
   `Material()`, чтение файлов, пересоздание таблиц на каждый кадр.
2. Замены: `GRM.Perf.Entities(class)` / `GRM.Perf.Players` (event-реестры
   по `OnEntityCreated/Removed`), `GRM.Perf.Material`, `GRM.Perf.EyeTrace`,
   кэш `DistToSqr`-проверок.
3. Своя периодическая работа в кадре — за ранним выходом по `CurTime()`
   (`if CurTime() < next then return end`), троттлинг 4–10 Гц, не 60.
4. `ShouldCollide` — ранний выход при пустой таблице пар.
5. `ENT:Think` — всегда `SetNextThink` или проверка `CurTime()`.
6. Не O(n²): вложенный обход (игроки × фракции) → обратный индекс,
    кэш строится по событию изменения.
7. Не `table.remove(q, 1)` в очереди — сдвиг O(n); снимать с хвоста.
8. Не создавать `Vector`/`Angle`/таблицы в render-кадре — готовить в
    `Think`/при изменении.

### 6.2 Диск

9. `file.Write` **синхронный** — сервер стоит. В горячем пути
    (`net.Receive`, чат-команда, `PlayerUse`, `KeyPress`, `PlayerDeath`,
    таймер < 30 с) — **запрещено**; только `GRM.Save.Register` +
    `GRM.Save.Mark` (писатель раз в секунду, один файл за тик).
10. `file.Write` не сообщает об успехе: **read-back + повторный decode**
    обязателен. Битый файл — в карантин, никогда не перезаписывать поверх.
11. Аудиты говорят прямо: основной риск фризов — не рендер, а дисковые
    записи (207 вызовов `file.Write` в 116 файлах, read-back у малой части).

### 6.3 Сеть и синхронизация

12. Широковещательный снимок — не на каждое изменение: `GRM.Perf.Coalesce`
    (0.25–0.5 с) → один пакет за тик. Дельта-синк: только изменённое,
    только получателям.
13. `net.WriteTable` без Stream — только разовые снимки по запросу
    админа; в цикле — запрещено. Три+ таблицы в пакете — Stream.
14. Change-only NW (`GRM.Perf.NWInt/NWString/...`): слать при изменении,
    не каждый тик.

### 6.4 Старты и фоновые задачи

15. Старт карты — `GRM.Boot` порциями (бюджет 2 мс/тик). Читать JSON на
    старте — одно; двадцать модулей одновременно — фриз загрузки.
16. Тяжёлый обход (сотни дверей, все энтити) — `GRM.Perf.Spread`.
17. Таймеры: нет тиков < 1 с «на всякий случай»; обходы в тике — только
    при наличии кого обслуживать (ранний выход по счётчику), «спящая»
    система — по хуку события.
18. Сканы каталогов (модели/материалы/звуки) — на клиенте по кадрам
    (несколько папок за тик), окно не фризится.
19. Шрифты: один `surface.CreateFont` на (имя, размер); не создавать в Paint.

## 7. Сеть и безопасность

1. Клиент — намерение; сервер повторно вычисляет: сущность (`requireEntity`),
   дистанция (`distance`), право (`capability`/permission), значения.
2. `GRM.Net.Guard(ply, key, opts)` до чтения payload: rate/burst/maxBits/
   requireEntity/distance/capability. **Fail-closed.**
3. Именование каналов — константы; регистрация на сервере.
4. Валидация строк: обрезать (`string.sub`), числа — `GRM.Net.Number`;
   длинные строки от клиента — лимит всегда.
5. `util.JSONToTable(txt, false, true)` — **только так** (игнор конверсии
   ключей; иначе SteamID64-ключи калечатся — «сага пропажи денег»).
6. Пути файлов от клиента — никогда; пути собирает сервер.
7. Деньги — только через Economy/Ledger API; составные изменения
   инвентаря — только транзакцией (многошаговые новые перемещения запрещены
   до появления Transaction).
8. Мутации значимого RP-состояния — в `GRM.Audit`.
9. Фото/файлы от игрока: кулдаун + лимит на игрока + лимит на сервер.
10. `RunString`/`CompileString` от клиента — запрещено (0 вхождений,
    поддерживаем).
11. Сторож: `tools/audit_net_guards.py`; порог голых обработчиков —
    `tools/luatest/sim_net_guard_watch.lua`.

## 8. Данные

1. **JSON имеет версию**; миграция в normalize-шаге; битый файл — карантин
   (`*.corrupt`), не поверх.
2. Читаем СНАЧАЛА, проверяем, потом удаляем старое (баг «телефоны исчезают
   при повреждении файла»: энтити сносились до разбора JSON).
3. Схемы: массивы записей предпочтительнее карт с числовыми ключами.
4. `data/`-пути: `data/grm_studio/`, `data/grm_industry/`, ... — каталог
   модуля; общие — `data/grm_core/`.
5. Понятные имена файлов: `map_<map>.json`, `orders_<map>.json`, `<slug>.json`.
6. Не хранить RP-состояние под `SteamID64` напрямую — CharacterKey.
7. Пути к `data/` в клиентских материалах — `file.Exists`/`Material` через
   pcall и fallback-надпись (обрывается молча).

## 9. UI — правила

### 9.1 Тема

- Палитра GRM/XUI: тёмный фон `8,14,23`, панель `16,27,42`, header `10,22,37`,
  текст `225,238,247`, muted `132,160,178`, акцент `48,204,255`, успех
  `64,222,147`, внимание `250,185,63`, ошибка `244,78,96`.
- Единственный шрифт — **Roboto**, всегда `extended = true` (кириллица),
  веса 400/500/700–800, размеры 11–24. Имена шрифтов — по префиксу модуля.
- Окна: `draw.RoundedBox` 8–9, кнопки 4, шапка `RoundedBoxEx` высотой 48–52,
  обводка `DrawOutlinedRect`, свой крестик (`ShowCloseButton(false)`).
- Подписи вкладок сразу в `AddSheet`; стиль GRM по всему модулю.

### 9.2 Окна и панели

1. Окна — `GRM.UI.Track`; повторный `Open` — показать существующее.
2. **Не вызывать `PerformLayout` напрямую** (GMod запрещает) и **не
   `SetTall` внутри `PerformLayout`** — вечный цикл и зависание клиента
   БЕЗ ошибки в консоли. Только `InvalidateLayout`.
3. `DScrollPanel`: **дети уходят в внутренний канвас** —
   чистить `panel:GetCanvas():GetChildren()`, а не `panel:GetChildren()`
   (удаление vbar → «Tried to use a NULL Panel», `OnMouseWheeled` nil).
   После ручной раскладки — `GetCanvas():SetTall(y)`.
4. Ширины/высоты при создании: панель может быть 0 до раскладки —
   `math.max(...)` от ширины родителя, иначе отрицательные `SetSize`.
5. Не `MakePopup` у панелей с клавиатурой/драгом, где нужно поймать
   отпускание мыши (меню по удержанию ЛКМ): отпускание не дойдёт, меню
   зависнет. Нужен `MouseCapture`.
6. Редакторы (drag/select поверх виджетов) — **хост-обводка**: клики и
   перетаскивание на `DPanel`-хосте, а не на `DButton`/`DTextEntry`
   (иначе теряется ввод/фокус/отрисовка).
7. Текст: `DLabel` вместо «нарисованного» текста; подписи-подсказки не
   налезают на ввод; проверять пересечение панелей.
8. Свеп/меню действий: одна логика для раскладки и выбора мышью
   (разные формулы = «жму одно, срабатывает другое»).
9. Костяные списки: строить ПОСЛЕ готовности скелета (GetBoneCount==0),
   перестраивать по событию, не один раз при открытии.
10. Перед предпоказом/предпросмотром: состояние модели из каталога, затем
    панель; незвучные звуки — `▶` с понятным «не нашлось».
11. «ТЕСТ ОКНА» — живые Derma-виджеты (не картинка макета): работоспособность
    проверяется до компиляции.

### 9.3 Поведение

- Не молчать об ошибке: `pcall` + уведомление + `ErrorNoHalt`; тихие отказы
  запрещены (игрок должен понимать, почему).
- Действие с понятной причиной отказа; недоступное — гаснет с причиной,
  а не исчезает молча.
- Валидация ввода: обрезка, `tonumber`, диапазоны; значение из поля —
  проверять до записи.
- Пересборка по событию изменения — раз, не в каждый кадр (флаг
  «завершён»/«грязно» + троттлинг 0.25 с).

## 10. Стенды

### 10.1 Правила

1. Стенд **воспроизводит баг до фикса** (на его собственной логике или
   откате фикса) — только тогда он сигнал.
2. **Откатная проверка**: временно вернуть баг → стенд краснеет → вернуть
   фикс. Стенд, который не краснеет, ничего не проверяет. Всегда.
3. Стенд устойчив: одна отсутствующая таблица не должна обрывать остальные
   проверки (`local X = istable(...) and ... or {}`).
4. Никаких копий проверяемой логики — проверка через ту же функцию/файл.
5. Проверять источник, а не комментарии: шаблон может совпасть с
   комментарием к фиксу — отрезать комментарии.
6. Итог — в конце строкой `НАЗВАНИЕ: N/N, провалов: M`, `os.exit`.
7. Полный прогон: `for f in tools/luatest/sim_*.lua; do luajit "$f"; done` —
   сравнить с базой: новых красных нет.

### 10.2 Ловушки поиска в Lua-тексте

| Ловушка | Правило |
|---|---|
| `(`/`)` в паттерне — метасимволы | `find(text, "ent:SetModel%(%\"\"%)")` или plain-флаг `find(..., 1, true)` |
| `%150` — обратная ссылка, «invalid capture index» | не извращаться с паттернами; plain-поиск |
| `"" or x` даёт `""` | явная проверка `== ""` |
| `string.lower` — ASCII | кириллица не приводится; не надеяться |
| `#t == 0` для таблицы со строковыми ключами | сериализация кривая; плотный массив 1..n |
| `sub(1,5)` режет UTF-8 байты | `GRM.UI.Utf8Sub` |
| `goto`/`until` — ключевые слова | `["goto"]`, `untilAt` |
| `d.ports.in` — `in` после точки | `d.ports["in"]` |
| `CompileString` возвращает функцию | `local fn,e = CompileString(...); pcall(fn)` |
| `net.ReadString` без обрезки | лимит всегда (сеть + память) |

### 10.3 Какие стенды-ворота обязательны к прогону

`sim_global_hygiene` (10), `sim_net_hook_conflicts` (9), `sim_forward_locals`,
`sim_net_guard_watch` (порог голых обработчиков), `sim_gmod_syntax`,
`sim_boot`, а также стенд конкретного модуля.
