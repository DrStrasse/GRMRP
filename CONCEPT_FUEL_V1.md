## 1. Что даёт simfphys (проверено по исходнику базы)

Данные каждой машины регистрируются таблицей, и в ней есть всё, что нужно
для заправки. Поля лежат в `Members`:

```lua
FuelFillPos  = Vector(-33.61, -45.1, 37.7),  -- где горловина бака
FuelType     = FUELTYPE_PETROL,              -- тип топлива
FuelTankSize = 80,                           -- объём бака в литрах
```

Константы типов (определяются базой в `simfphys/base_functions.lua`):

| Константа | Значение |
|---|---|
| `FUELTYPE_NONE` | 0 |
| `FUELTYPE_PETROL` | 1 |
| `FUELTYPE_DIESEL` | 2 |
| `FUELTYPE_ELECTRIC` | 3 |

При спавне база раскладывает эти поля прямо на сущность и поднимает их в
сеть (`entities/gmod_sent_vehicle_fphysics_base/spawn.lua`, строки 149–155):

```lua
local tanksize = self.FuelTankSize and self.FuelTankSize or 65
local fueltype = self.FuelType and self.FuelType or FUELTYPE_PETROL
self:SetMaxFuel( tanksize )
self:SetFuel( self:GetMaxFuel() )
self:SetFuelType( fueltype )
self:SetFuelPos( self.FuelFillPos and self.FuelFillPos or Vector(0,0,0) )
```

То есть на живой машине доступно:

| Что | Как прочитать |
|---|---|
| **Мировая точка горловины** | `ent:GetFuelPos()` |
| Локальная точка горловины | `ent:GetFuelPortPosition()` (NetworkVar) |
| Литры в баке | `ent:GetFuel()` |
| Объём бака | `ent:GetMaxFuel()` |
| Тип топлива | `ent:GetFuelType()` |
| Литраж и тип в записи | `ent:GetFuel()`, `ent:SetFuel(n)` |
| Полная таблица машины | `ent.VehicleTable` → `.Members.FuelFillPos` |

**Это ключевая находка:** точка горловины не вычисляется и не угадывается —
её даёт сама машина, одна на модель, ровно там, где её поставил автор
конверсии.

Две оговорки, их надо учесть:

- Если `FuelFillPos` в конверсии не задан, база ставит `Vector(0,0,0)` —
  то есть origin машины. Значение `GetFuelPos()` при этом валидно по типу,
  но бессмысленно по сути. Нужен фолбэк и пометка «горловина неизвестна».
- simfphys заканчивает инициализацию асинхронно: сразу после выдачи машины
  поля могут быть ещё не проставлены. Это уже встречалось в автопарке
  (`sh_grm_fleet.lua:1250`).

## 3. Дыры

### 3.1 Шланга как объекта нет — он только нарисован

Серверные функции, которые по имени отвечают за шланг, пустые
(`sh_grm_fuel.lua:259`, `:263`):

```lua
function F.AttachHose(pump)
    F.ClearHose(pump)
end

function F.HoseToTank(pump)
    F.ClearHose(pump)
end
```

Обе только удаляют веревку. Никакой привязки, никакой физики, никакой
проверки длины. Весь «шланг с провисом» из шапки файла — это клиентский
`render.DrawBeam` в `ENT:Draw()`. Он не знает про препятствия, не
ограничен по длине и исчезает, если колонка вышла из поля зрения (PVS).

### 3.2 Точка бака — догадка, не горловина

`sh_grm_fuel.lua:92`:

```lua
function F.TankWorld(ent)
    local mn, mx = ent:OBBMins(), ent:OBBMaxs()
    return ent:LocalToWorld(Vector(mn.x + 12, mx.y - 8, (mn.z + mx.z) * 0.35))
end
```

И ровно та же формула продублирована в пистолете
(`weapon_grm_fuel_nozzle.lua:36`). Это «12 юнитов от передней границы
габарита, 8 юнитов от правого борта, 35% высоты». К реальной горловине
отношения не имеет: у части машин она слева, у части спереди, у части
совсем в другом месте. `FuelFillPos` из тех же машин, что стоят на сервере:

```
Vector(17.64, -14.55, 30.06)      -- одна модель
Vector(32.82, -78.31, 81.89)      -- другая
Vector(-39.07, -108.1, 60.81)     -- третья
Vector(-61.39,  49.54, 15.79)     -- дизель
```

Разброс по всем трём осям, включая знак Y. Догадка не может попасть.

Отсюда и симптом: игрок подходит к правому заднему крылу, потому что
подсказка говорит «зад крыла», а пистолет либо не находит машину вовсе,
либо находит, но шланг тянется в пустоту.

### 3.3 Горловину игрок не видит

Ни маркера, ни подсветки, ни подсказки у самой точки. Подсказка в
пистолете — «Поднеси пистолет к горловине бака (зад крыла)» — ориентирует
на точку, которой нет.

### 3.4 Объём бака — константа 100 литров

`sh_grm_fuel.lua:88`:

```lua
function F.TankSize()
    return 100
end
```

У simfphys свой `FuelTankSize` на модель (65 по умолчанию, 80 у примера из
документации). Итог: в одной машине по документации 80 л, GRM нальёт 100.

### 3.5 Тип топлива угадывается по названию

`sh_grm_fuel.lua:78` ищет в имени класса и модели подстроки `electric`,
`tesla`, `truck`, `kamaz`, `ural`, `diesel`. У simfphys тип задан числом и
проставлен в сеть (`ent:GetFuelType()`). Угадывание даёт ложные отказы
«Не тот тип» на машине, которая по данным — бензин.

### 3.6 Два независимых бака

Это главное следствие. У simfphys есть свой учёт: `GetFuel/SetFuel`,
`GetMaxFuel`, и база сама расходует топливо и глохнет при нуле. У GRM —
свой, в `grm_fuel.json` по UID машины (`F.Data[uid].liters`, `F.ApplyNW`).

Они не связаны. `F.AddLiters` меняет только запись GRM; simfphys-бак при
этом остаётся пустым. И наоборот: `SetFuelUse` и simfphys-расход GRM не
трогает вовсе (поиск по всему `lua/` — ни одного обращения).

Практически это значит, что машина может показывать полный бак в HUD GRM и
при этом не заводиться «по simfphys», либо ехать на пустом GRM-баке, пока
simfphys считает своё.

### 3.7 Стенд не покрывает заправку

`sim_fuel_ownership.lua` проверяет только владение, цену и кассу. Ни
позиции горловины, ни шланга, ни самой заливки в стендах нет — ровно та
причина, по которой дыры из 3.1–3.6 дожили до сих пор.

## 4. Предложение

### 4.1 Источник истины — свой учёт поверх бака машины

**Решение владельца: «свой учёт поверх».** Значение храним сами —
администрация может поправить литраж руками, и бак переживает рестарт и
выдачу из гаража. Но у живой машины оно обязано совпадать с её собственным
баком, иначе HUD показывает одно, а simfphys считает другое.

Правило синхронизации:

- **один раз** при первом обращении к машине отдаём сохранённое значение
  в её бак (`ent:SetFuel`);
- **дальше зеркалим** её бак к себе, чтобы расход на ходу попадал в учёт;
- при заливке пишем в обе стороны сразу.

Объём бака и тип топлива берём у машины (`GetMaxFuel`, `GetFuelType`), а не
из константы и не угадыванием по имени. Фолбэк 100 л и угадывание по имени
остаются только для ванили, у которой своего бака нет.

### 4.2 Горловина берётся из машины и показывается игроку

```
F.FillPort(veh) -> pos, normal, known
```

Порядок:
1. `veh.GetFuelPos` → берём `veh:GetFuelPos()`.
2. Проверяем на бессмыслицу: точка на нуле локальных координат при
   ненулевом габарите, либо за пределами габарита → `known = false`.
3. Фолбэк — нормаль берём трассировкой от центра габарита к точке, чтобы
   знал/шланг подходил снаружи, а не изнутри кузова.
4. Для ванили — прежний расчёт по габариту, с `known = false`.

Игроку горловину показываем: при пистолете в руках подсвечивать точку у
ближайшей машины в радиусе и писать, с какой она стороны. Без этого
«подойди к горловине» останется угадайкой — у половины машин она слева.

### 4.3 Шланг — настоящий, а не нарисованный

**Решение владельца: длина одна на все колонки** (`F.HoseLength = 360`).

Предлагаю два слоя, потому что физическая веревка на каждом кадре дорога и
плохо ведёт себя на сервере:

- **Физика:** веревка от колонки к пистолету создаётся в момент выдачи
  (`F.AttachHose` перестаёт быть заглушкой), с запасом длины, равной
  радиусу шланга. Она даёт натяжение и не даёт уйти дальше, чем шланг
  позволяет — это и есть «крепление».
- **Картинка:** провес рисуется на клиенте, как сейчас, но считается по
  реальной длине веревки, а не по формуле.

Шланг физически не дотягивается, если машина далеко: `HoseToTank` не
создаёт веревку и возвращает false. Раньше радиус был зашит числами 420 и
430 в двух местах, и «шланг не дотягивается» было сообщением, а не
физикой.

### 4.4 Вставка в бак — по горловине, а не по «очутился рядом»

Сейчас `FindVehicle` проверяет расстояние от игрока до догаданной точки
(90/110/130 юнитов) и всё. Предлагаю: луч из глаз игрока; попал в машину и
точка попадания рядом с горловиной (или игрок стоит рядом с горловиной) →
можно вставлять. Радиус берём от высоты машины, а не константой: у грузовика
горловина высоко, игрок физически не подойдёт на 90 юнитов.

### 4.5 Что не трогаем

Экономику станций — владение, выкуп, цену за литр, кассу, `StationID` —
предлагаю оставить как есть. Она проверяется стендом и жалоб на неё не
было. Меняем только физику процесса: бак, горловину, шланг, вставку.

### 4.6 Шланг на колонке, а не в руках

**Заказ владельца:** «шланг не должен сам выходить из бака и не должен
отдаваться игроку».

Раньше колонка выдавала игроку оружие-пистолет, он носил его к машине и
вставлял в бак. Таймер заливки каждую итерацию проверял расстояние до
игрока и выдёргивал пистолет: «Отошёл от бака», «Шланг натянулся». Пистолет
в руках — это и есть «отдаётся игроку»: предмет, который можно уронить,
унести и потерять.

Теперь: игрок подходит к колонке и жмёт `E` — шланг сам тянется к горловине
машины (той, на которую смотрит игрок, иначе ближайшей). Заливка идёт без
игрока: он может сидеть в машине, отойти, уехать по делам.

Шланг выходит из бака только в двух случаях:

- **осознанно** — повторное `E` на колонке;
- **по физике** — машину утащили дальше длины шланга.

Полный бак и пустой кошелёк заливку останавливают, но шланг **остаётся** в
баке и ждёт человека: колонка сообщает об этом один раз.

Оружие `weapon_grm_fuel_nozzle` удалено: оно больше никому не выдаётся.

Стенд `tools/luatest/sim_fuel_port.lua` — 41 проверка. До этого по
заправке существовал только `sim_fuel_ownership` (владение и цена), поэтому
дыры и жили незамеченными. Откат каждой правки краснит стенд.
