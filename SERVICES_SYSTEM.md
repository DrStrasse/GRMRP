## 2. Данные

### `data/grm_services/services.json`

```
{ version = 1,
  services = [ { id, name, category, price, provider, desc, enabled, created, createdBy } ],
  access   = { "<Фракция>" = { canService, canInvoice, canDiploma,
                               categories = {id=true}, maxInvoice, institution, note } } }
```

### `data/grm_services/invoices.json`

```
{ version = 1, nextID = N,
  invoices = [ { id, target, targetName, issuer, issuerName, faction, serviceID,
                 title, amount, paid, status, issued, closed, note } ] }
```

`status ∈ unpaid | paid | cancelled`. Ключ плательщика — `GRM.Identity.CharacterKey`
(`SteamID64:charN`): счёт принадлежит персонажу, а не аккаунту.

### `data/grm_services/diplomas.json`

```
{ version = 1, nextNumber = N,
  diplomas = [ { number, seq, graduate, graduateName, institution, faction,
                 specialty, qualification, level, form, grade, paid, invoiceID,
                 issuer, issuerName, signedBy, issued, revoked, revokeReason, note } ] }
```

Номер бланка: `ГД-<год>-<6 цифр>`, например `ГД-2026-000123`. Номер сквозной,
после перезагрузки продолжается с максимума (проверено тестом).

**Миграция не требуется:** это новые файлы, старых форматов у них нет.
Совместимость по чтению обеспечена: загрузчик принимает и `{invoices=[…]}`, и голый
массив, битый json уводится в `*.corrupt.<ts>` без потери исходника.
Во фракциях добавлены три поля (`ServiceAccess`, `InvoiceAccess`, `DiplomaAccess`) —
`ensureDefaults` проставляет им `false`, старые `factions.json` читаются без изменений.

## 3. Права

Два уровня, чтобы админ мог быстро включить организацию и точно её настроить.

**Рубильник — в меню фракций** (`/factions` → вкладка доступов, только суперадмин):
«Оказание услуг», «Выставление счетов», «Выдача дипломов». Снятая галка гасит
возможность независимо от детальной настройки.

**Детально — в банкомате**, вкладка «Надзор» → «Доступы организаций»: категории услуг,
предел суммы одного счёта, официальное название учреждения для бланков.

Кто что может:

| Оплата своих штрафов и счетов | ✔ | ✔ | ✔ | ✔ |
| Заказ услуги из витрины | ✔ | ✔ | ✔ | ✔ |
| Проверка чужого диплома по номеру | ✔ | ✔ | ✔ | ✔ |
| Выставление счёта | — | ✔¹ | ✔¹ | ✔ |
| Правка каталога услуг | — | — | ✔¹ | ✔ |
| Выдача диплома | — | ✔¹ | ✔¹ | ✔ |

## 4. Деньги

`GRM.Services.Charge(ply, amount, source, reason)` — единая касса:

* `"bank"` — только со счёта;
* `"cash"` — только наличные;
* `"auto"` (по умолчанию) — сначала счёт, недостающее наличными; при неудаче
  снятое возвращается на счёт.

Распределение оплаченного счёта: `ProviderShare = 0.80` в бюджет фракции-исполнителя,
остаток — в казну (`E.StateAdd`). Счёт без фракции целиком уходит государству.

Штрафы гасятся через `S.PayFine`: реестр штрафов умеет списывать только наличные,
поэтому недостающее сначала переводится со счёта в карман, а бухгалтерия остаётся
в одном месте — `GRM.Wanted.Fines.Pay`.

Новое в экономике: `E.BankTake(ply, amount, reason)` и `E.BankGive(...)` — безналичное
списание и зачисление, не превращающие деньги в наличные (в отличие от `BankWithdraw`).

## 5. Меню банкомата

Открывается при `ENT:Use` банкомата, командой `grm_atm` и плиткой «Госуслуги» в
компьютере. Стиль — палитра `GRM.UI.Theme`, боковое меню вкладок, окно 900×640.

| Вкладка | Содержимое |
|---|---|
| Мой счёт | Наличные и счёт, внести / снять / перевести |
| Задолженность | Штрафы и счета, оплата поштучно или «Оплатить всё» |
| Госуслуги | Витрина с фильтром по категориям, заказ с оплатой |
| Дипломы | Свои дипломы, проверка чужого по номеру |
| Организация | Счета, каталог услуг, реестр выданных дипломов (по доступам) |
| Надзор | Доступы фракций, реестр счетов, реестр дипломов (суперадмин) |

**Выписка дипломов в банкомате не ведётся** (см. раздел 12). Банкомат — касса:
оплата обучения, проверка бланка по реестру, просмотр выданных. Сам бланк
заполняют в учреждении образования.

### Сеть

| Строка | Направление | Полезная нагрузка |
|---|---|---|
| `GRM_ATM_Open` | S → C | `Entity`, `Table` (снимок) |
| `GRM_ATM_Data` | S → C | `Table` (снимок) — обновление после действия |
| `GRM_ATM_Act` | C → S | `String` action, `Table` args |
| `GRM_ATM_Result` | S → C | `Bool` ok, `String` сообщение |

Действия: `deposit`, `withdraw`, `transfer`, `pay_fine`, `pay_invoice`, `pay_all`,
`order_service`, `issue_invoice`, `cancel_invoice`, `upsert_service`, `delete_service`,
`issue_diploma` (устарело, см. раздел 12), `revoke_diploma`, `check_diploma`, `admin_set_access`,
`admin_edit_invoice`, `admin_delete_invoice`, `admin_edit_diploma`,
`admin_delete_diploma`, `admin_restore_diploma`, `refresh`.

Защита: дистанция `UseRange = 200` проверяется и при открытии, и при каждом действии;
rate-limit 0.35 с; права проверяются на сервере, клиентские вкладки — только витрина.

## 6. Связь с электроникой

`A.TerminalReady(ent)` отказывает, если:

* терминал заблокирован инкассацией (`GRM_IncassLocked`);
* устройство обесточено (`GetDeviceActive() == false`);
* устройство не в сети (`E.IsOnline`).

Банкомат без `DeviceID` (не заведён как устройство) работает автономно — старые
карты не ломаются.

## 9. Сценарий «образовательное учреждение»

1. Игроки подали заявку в Discord, выбрали локацию — админ одобрил.
2. Админ создаёт фракцию и в `/factions` включает ей «Оказание услуг» и «Выдача дипломов».
3. В банкомате → «Надзор» → «Доступы организаций» задаёт официальное название
   («Государственный университет Гродно»), категорию «Образование», предел счёта.
4. Ректор в кабинете организации заводит услугу «Обучение по специальности…» с ценой.
5. Житель видит услугу в витрине банкомата, заказывает — деньги уходят: 80 % в бюджет
   университета, 20 % в казну. Либо учреждение выставляет счёт вручную; либо обучение
   бесплатное — тогда счёт не нужен.
6. По окончании обучения преподаватель выписывает диплом **в учреждении
   образования** — на компьютере деканата (`grm_comp_education`) или во вкладке
   «Учреждение образования» меню фракций, — указав счёт об оплате
   (по неоплаченному счёту диплом не выдаётся). Выпускник выбирается из реестра
   персонажей: онлайн быть не обязан.
7. Диплом попадает в государственный реестр; любой может проверить его по номеру
   командой `/diploma ГД-2026-000123` или во вкладке «Дипломы».

## 11. Ошибка Q-меню `dscrollpanel.lua:111` — разбор и фикс

**Симптом:** `[ERROR] lua/vgui/dscrollpanel.lua:111: Tried to use a NULL Panel!`
в цепочке `GetTall → PerformLayoutInternal → dscrollpanel.lua:135`, повторяется
пачками (раскладка вызывается каждый кадр, пока окно живо).

**Корень.** `DScrollPanel` держит служебные панели: холст `pnlCanvas` и полосу
`VBar`. Метод `GetChildren()` возвращает **их**, а не добавленные строки —
элементы лежат внутри холста. `PerformLayoutInternal` читает
`self.pnlCanvas:GetTall()`; если холст удалён, обращение к мёртвой панели роняет Lua.

Найдено и закрыто четыре причины:

1. **Очистка списка настроек тула** (`showToolSettings`) шла циклом
   `for _, ch in ipairs(settingsBody:GetChildren()) do ch:Remove() end` — это
   сносило холст. → `settingsBody:Clear()` с фолбэком через `GetCanvas()`.
2. **Панель тула** добавлялась `SetParent(settingsBody) + Dock(TOP)`, минуя холст:
   раскладка её не видела, `:Clear()` не удалял. → `settingsBody:AddItem(CP)`.
3. **Общая панель `controlpanel.Get(name)`** делится с ванильным Q-меню. При смерти
   фрейма в обход `CloseMenu()` (таймер кликера, смерть игрока, `SetDeleteOnClose(true)`)
   она уезжала в могилу вместе с окном. → `f.OnRemove` отвязывает `QM._toolCP`
   (`SetParent(nil)`, `SetVisible(false)`) и сбрасывает `QM._settingsBody`.
4. **Заглушка «ничего не найдено»** во вкладке каталога добавлялась прямым ребёнком
   `DScrollPanel`, а `rebuildGrid` чистил только `DIconLayout` — сироты копились при
   каждом поиске. → заглушка уходит в холст через `AddItem` и снимается
   `clearEmptyBox(sc)` перед перестройкой.

Попутно в меню банкомата устранён тот же класс дефекта: `card()` создавал панель
ребёнком скролла и **дополнительно** отдавался в `sc:AddItem()` — двойное родительство.
Теперь `card()` не назначает родителя, если это скролл: парентит `AddItem`.

**Правила** (закреплены тестом):
* чистить `DScrollPanel` только `:Clear()` либо `GetCanvas():GetChildren()`;
* добавлять элементы только `:AddItem()`, не `SetParent()+Dock(TOP)`;
* общие панели (`controlpanel.Get`) отвязывать в `OnRemove`.

**Тест:** `luajit tools/luatest/sim_qmenu_scroll.lua` — **32/32**. Модель VGUI
повторяет поведение движка; тест 1 **воспроизводит падение** на старом способе
очистки, тесты 2–6 подтверждают корректность нового, тест 7 сканирует исходники
проекта на возврат запрещённых паттернов.

## 12. Рабочее место учреждения образования (пересмотр выдачи дипломов)

### Что было не так

Первая редакция выдавала дипломы через банкомат. Три претензии подтвердились кодом:

1. **Выпускника нельзя было выбрать, если он офлайн.** Список строился из
   `player.GetAll()` (`sh_grm_atm.lua`, снимок), то есть из живых сессий. Диплом же
   принадлежит **персонажу** (`CharacterKey = SteamID64:charN`), а не сессии.
   Выписать документ отчисленному, уехавшему или просто вышедшему игроку было
   невозможно, а имя в бланке бралось из ника Steam.
2. **Банкомат — неподходящее место.** Это касса. Выписка государственного бланка
   в кассе ломает ролевую логику: у деканата нет причин идти к банкомату,
   а у банкомата нет причин знать про специальности и квалификации.
3. **Форма не помещалась в окно.** Часть полей версталась абсолютными `SetPos`
   с координатами до 674 px при полезной ширине тела окна ≈ 656 px — правый край
   срезался (видно на скриншоте: «Цена», «Сохранить услугу», «Выдача дипломов»).

### Что сделано

**Разделение ответственности:**

| Место | Задачи |
|---|---|
| Банкомат (`grm_atm`) | оплата обучения по счёту, проверка бланка по номеру, просмотр своих и выданных дипломов |
| Учреждение образования | заполнение и выписка бланка, реестр учреждения, аннулирование |

**Два входа в рабочее место** (интерфейс общий, собирается `GRM.Education.BuildWorkspace`):

* **Компьютер деканата** — сущность `grm_comp_education` («GRM — RP» в спавн-меню).
  Открывается `E`, уважает электронику: обесточенный компьютер не открывается.
* **Вкладка «Учреждение образования»** в меню фракций — через штатный хук
  `GRM_FactionsAdmin_BuildTabs`, тем же способом, что «Доступ к аресту» и «Экономика».

**Выбор выпускника — из реестра персонажей.** `GRM.Services.CharacterRegistry()`
сливает три источника по ключу `CharacterKey`:

1. онлайн-игроки — свежий ник и признак «в сети»;
2. `GRM.Documents.Registry.passports` — офлайн-персонажи с паспортным ФИО;
3. составы фракций (`Members`) — курсанты без паспорта.

Имя выбирается по приоритету **паспорт → RP-имя → ник**. В интерфейсе это
комбобокс с полем поиска (по имени, фракции, ключу); онлайн помечены точкой,
фракция показана в скобках. Тем же реестром теперь пользуется выставление счетов,
поэтому счёт офлайн-персонажу получает имя «Иоганн Мюллер», а не `7656…:char1`.

**Права не дублируются.** Единственный источник истины остался прежним —
`GRM.Diplomas.CanIssue` (флаг `canDiploma` у фракции + байпас суперадмина).
`GRM.Education.CanUse` вызывает его же. Аннулирование по-прежнему доступно
руководителю учреждения и суперадмину.

**Верстка от фактической ширины.** Абсолютные `SetPos` заменены на раскладку
в `PerformLayout(self, w)`: колонки считаются от реальной ширины карточки,
кнопки прижимаются к правому краю. Исправлено и в новом модуле, и в банкомате
(форма услуги, доступы организаций, карточки реестра).

## 13. Доводка выдачи дипломов: кнопка, спавн компьютера, перманентность

### Замечание 1 — «кнопки выдать нет»

Кнопка **«ВЫДАТЬ ДИПЛОМ»** в коде была, но на экран не попадала. Форма выписки
верстается сверху вниз: учреждение и выпускник → специальность → квалификация →
уровень и форма → оценка и стоимость → кнопка. Последний ряд оказывался на
`y = 310`, а карточка создавалась высотой **300**. VGUI обрезает детей по границе
родителя, поэтому кнопка и подсказка рядом с ней не рисовались **никогда** —
ни при каком размере окна и ни при какой прокрутке.

Исправлено двумя шагами:

* базовая высота карточки увеличена до 360;
* `PerformLayout` теперь досчитывает фактическую высоту содержимого
  (`need = y + 32 + 14`) и подгоняет карточку под неё. Добавление новых полей
  больше не может «съесть» нижний ряд.

### Замечание 2 — компьютера деканата не было в служебном инструменте

Класс `grm_comp_education` не был зарегистрирован **ни в одном** из трёх реестров,
где положено объявлять служебное оборудование. Добавлено во все три:

| Файл | Реестр | Следствие пропуска |
|---|---|---|
| `lua/weapons/gmod_tool/stools/grm_service_tool.lua` | `TYPES.education` | компьютер нельзя поставить инструментом |
| `lua/autorun/sh_grm_perm_entities.lua` | `PERM_CLASSES` | не сохраняется на карту, пропадает после рестарта |
| `lua/autorun/sh_grm_prop_protect.lua` | список защищаемых классов | любой игрок может удалить/утащить физганом |

Параметры типа: заголовок по умолчанию «УЧРЕЖДЕНИЕ ОБРАЗОВАНИЯ • ДЕКАНАТ»,
модель `models/props/cs_office/computer.mdl`. Ставить может суперадмин или лидер
фракции — правило общее для всего служебного оборудования.

### Замечание 3 (найдено попутно) — заголовок не переживал рестарт

Инструмент позволяет задать «Заголовок на экране», но перманентное сохранение
писало только класс, модель и позицию. После рестарта сервера у **всех семи**
служебных компьютеров на табличке снова стоял заводской текст.

Добавлены делегаты `GRM.PermData.Extract` / `Apply` для всех служебных
компьютеров: заголовок пишется в `rec.data.computerName` и применяется при
восстановлении. `NetworkVar("String", 0, "ComputerName")` у сущностей уже был,
менять их не потребовалось. Табличка `grm_comp_education` теперь тоже читает
заданное имя, а на дефолт откатывается только если имя пустое.

### Пошаговый сценарий выдачи диплома

1. **Поставить компьютер.** `Q` → вкладка **GRM** → **GRM Служебное оборудование**.
   В списке выбрать **«Компьютер Учреждения образования (деканат)»**, при желании
   задать свой заголовок и включить «Сделать перманентным». ЛКМ по поверхности.
2. **Выдать фракции право выписки.** Флаг `canDiploma` — либо командой
   `/svc_access <Фракция> canDiploma 1`, либо в меню фракций → админ-вкладка
   **«Доступы организаций»**. Там же задаётся название учреждения, которое
   попадёт в бланк.
3. **Открыть рабочее место.** `E` по компьютеру (компьютер должен быть запитан),
   либо меню фракций → вкладка **«Учреждение образования»**.
4. **Заполнить бланк** на вкладке «Выписать диплом»: выпускник выбирается из
   реестра персонажей (в том числе офлайн, с поиском), затем специальность,
   квалификация, уровень, форма, оценка и стоимость обучения.
5. **Нажать «ВЫДАТЬ ДИПЛОМ».** Номер вида `ГД-2026-000123` присваивается
   автоматически. Если указана стоимость — выпускнику выставляется счёт,
   оплачивается через банкомат.
6. **Проверить.** Вкладка «Реестр учреждения» — все выданные бланки, вкладка
   «Проверка» и банкомат — поиск по номеру. У выпускника — `/mydiplomas`.

## 14. «Мои дипломы» — просмотр документа игроком

До этого посмотреть свой диплом можно было только чат-командой `/mydiplomas`,
которая печатала текст в чат. Это выбивалось из остальной системы: паспорт,
удостоверение, военный билет, права и медкарта открываются **кнопкой в C-меню**
и показываются визуальным бланком.

Диплом приведён к тому же виду.

### Кнопка в C-меню

В блок личных документов `sh_grm_ctx.lua` добавлена кнопка `doc_self_diploma`:

* подпись динамическая — «Мой диплом» при одном документе,
  «Мои дипломы (N)» при нескольких;
* показывается, только если у персонажа есть хотя бы один бланк
  (сервер отдаёт `diplomaCount` в общем снимке C-меню) и если игрок
  не смотрит на другого игрока — ровно так же ведут себя остальные
  личные документы;
* цвет золотой, чтобы не путать с синими правами и красным паспортом.

### Окно просмотра

`GRM.Education.OpenMine` рисует каждый диплом **бланком**, а не строкой списка:
тёплая «бумага», золотая рамка и корешок, заголовок «ГОСУДАРСТВЕННЫЙ ДИПЛОМ»,
поля в две колонки (подпись — значение). Аннулированный бланк перекрашивается
в красный, получает водяной знак «АННУЛИРОВАН» и строку с причиной.

Раскладка идёт через `PerformLayout(self, w)` от фактической ширины, высота
бланка считается по числу полей — правый край не режется, длинное примечание
не выходит за карточку.

### Права и данные

Личный просмотр **не требует никаких прав**: это собственный документ
персонажа. `canDiploma` нужен только для выписки. Отдельная пара сетевых
строк `GRM_Edu_MyAsk` / `GRM_Edu_MyData` с тем же rate-limit 0.35 с; сервер
берёт список через `GRM.Diplomas.For(ply, true)` и отдаёт **только бланки
этого персонажа**. Уровень и форма обучения переводятся в читаемые названия
на сервере, чтобы клиент не зависел от снимка рабочего места.

Аннулированные бланки владельцу показываются намеренно: иначе документ просто
исчезал бы, и игрок считал бы это багом.

### Способы посмотреть диплом

| Способ | Что показывает |
|---|---|
| **C-меню → «Мои дипломы»** | визуальные бланки всех своих дипломов |
| консоль `grm_mydiplomas` | то же окно |
| `/mydiplomas` | текстом в чат (оставлено) |
| банкомат, вкладка «Дипломы» | свои дипломы и проверка чужого по номеру |
| `/diploma <номер>` | проверка любого бланка по номеру |

### Тесты

* `sim_education` — **60/60**: добавлен блок «Мои дипломы» (владелец видит свой
  бланк, посторонний не видит чужих, аннулированный остаётся виден со статусом,
  уровень и форма приходят названиями, права `canDiploma` для просмотра не нужны).
* `sim_edu_ui` — **45/45**: окно бланков строится, поля не выходят за границы,
  номер и причина аннулирования отображаются, пустой список не роняет окно,
  кнопка C-меню на месте.

## 15. Предъявление диплома, диплом в досье и редактор оперативного дела

Задача 8 закрывает четыре вопроса: показ диплома собеседнику, визуальный бланк,
учёт образования в досье спецслужб и полноценный редактор оперативного дела.

### 15.1. Предъявление диплома другому игроку

Раньше диплом можно было только посмотреть самому. Теперь он предъявляется так же,
как паспорт или военный билет — тем же сценарием, что и в `sh_grm_documents.lua`.

* Сетевые строки: `GRM_Edu_ShowAsk` (клиент → сервер) и `GRM_Edu_ShowView`
  (сервер → цель).
* Правила показа повторяют документные: цель — игрок под прицелом, живой,
  дистанция **не более 200 юнитов**. Показать можно **только свой** бланк:
  сервер сверяет номер диплома с выпускником, а не доверяет клиенту.
* Действие сопровождается `/me`-объявлением в радиусе 400 юнитов
  («* Иоганн Мюллер предъявляет диплом …»), как и остальные документы, — чтобы
  окружающие видели сцену отыгрыша.
* Если у персонажа несколько дипломов, C-меню показывает выбор конкретного бланка
  (`EDU.PickForShow`), а не отправляет первый попавшийся.

**C-меню.** В блоке действий над игроком появилась кнопка
**«Предъявить диплом: <имя>»** (`doc_diploma`). Она видна, когда игрок под
прицелом и у предъявителя есть хотя бы один бланк (`diplomaCount > 0`).
Рядом сохраняется кнопка «Мои дипломы» (`doc_self_diploma`) для просмотра без цели.

### 15.2. Визуальный бланк вместо набора строк

Диплом рисуется процедурным бланком `diplomaBlank` (введён в разделе 14):
«бумажный» фон, золотая рамка и корешок, поля в две колонки, автоматическая
высота под содержимое. Аннулированный бланк перекрашивается в красный и получает
водяной знак. Окно предъявления (`EDU.OpenShown`, 660×420) **переиспользует ту же
отрисовку**, поэтому получатель видит тот же документ, что и владелец, — расхождения
между «своим» и «показанным» видом исключены по построению.

### 15.3. Образование в оперативном досье

Досье на компьютере спецслужб (`grm_comp_security`) состояло из шести разделов
и не содержало сведений об образовании. Добавлены два новых:

* **7. ОБРАЗОВАНИЕ И КВАЛИФИКАЦИЯ** — номер диплома, учебное заведение,
  специальность, уровень и форма обучения, дата выдачи, отметка `[АННУЛИРОВАН]`.
* **8. ОПЕРАТИВНОЕ ДЕЛО** — статус, уровень угрозы, дата обновления, фабула
  и последние 10 пометок.

Дипломы собираются на сервере (`grm_comp_security/init.lua`) только по онлайн-списку —
иначе net-сообщение упрётся в лимит на населённом сервере.

### 15.4. Редактор оперативного дела

Новая вкладка терминала — **«Редактор дела»**. Сотрудник выбирает субъекта
(онлайн-игроки плюс субъекты, на которых дело уже заведено, даже офлайн) и:

* правит **фабулу** — основания разработки, связи, задачи (до 4000 символов);
* выставляет **статус**: в работе / наблюдение / приостановлено / закрыто / в архиве;
* задаёт **уровень угрозы** 0–5 (значение зажимается и при вводе, и при чтении файла);
* ведёт **хронологию пометок** — каждая с датой, автором и текстом (до 1000 символов,
  хранится последние 200);
* кнопкой **«СОХРАНИТЬ ДЕЛО В БАЗУ СПЕЦСЛУЖБЫ»** передаёт дело в общую базу.

Дело живёт в `data/grm_wanted/special.json` — то есть видно **всем агентам**, а не
только автору, и переживает перезаход и рестарт сервера. Каждое сохранение и каждая
пометка дублируются в закрытый журнал спецслужбы (`SS.Note`, операции `case_save`,
`case_note`, `case_note_del`, `case_delete`).

**Права.** Заводить дело, править его и вносить пометки может любой агент
(`SS.IsAgent`). Удалять отдельные пометки и дело целиком — **только суперадмин**:
это защита от заметания следов внутри самой спецслужбы.

**API** (`GRM.SpecialService`): `CaseOf(key)`, `CaseSave(actor, key, fields)`,
`CaseAddNote(actor, key, text)`, `CaseRemoveNote(actor, key, index)`,
`CaseDelete(actor, key)`, `CaseRows(limit)`, `CaseStatusName(id)`, `CaseStatuses`.
Хуки: `GRM_SS_CaseSaved`, `GRM_SS_CaseNoteAdded`.

### 15.5. Миграция `special.json` v1 → v2

Формат вырос: добавлен ключ `cases`. Миграция выполняется в `normalize()` —
у старого файла ключа просто нет, он создаётся пустым, а `agents`, `journal`
и `covers` остаются нетронутыми. Версия при первом сохранении поднимается до 2.
Отдельного шага обслуживания не требуется, откат данных невозможен.

Сетевой протокол `GRM_SpecService_Act` расширен пятым полем `extra` (таблица) —
длинная фабула не помещалась в строковое поле. Поле пишется всегда, поэтому
рассинхрона между клиентом и сервером не возникает.

## 16. Перма-проп-инструмент GRM (Задача 9)

Собственный инструмент закрепления объектов на карте. Закреплённый объект
переживает рестарт сервера и `cleanup`, синхронизирован с проп-протектором
`GRM.PropProtect` и с системой данных экземпляров `GRM.PermData`.

Концепция целиком — в `CONCEPT_PERM_TOOL.md`. Ниже — что фактически сделано.

### 16.1. Что было сломано

| Код | Дефект | Следствие |
|-----|--------|-----------|
| Д17 | `GRM.Perm.Add/Remove` не существовали | Галочка «сохранить на карте» в служебном инструменте — пустышка: `pcall` молча глотал вызов несуществующей функции |
| П1 | `spawnAll` звал `MarkServerEntity` для всех записей | После рестарта владелец терял доступ к собственной запермленной двери: `CanInteract` проверяет `IsServerEntity` раньше `IsOwner` |
| П2 | `/permremove` удалял сам объект | Нельзя было снять закрепление, чтобы подвинуть постройку |
| П3 | Записи без идентификатора | Поиск «класс + 6 юнитов»: сдвинул объект — запись потерялась |
| П4 | Один делегат `Extract`/`Apply` на класс | На `prop_physics` FFD-двери и перм-тул затирали друг друга по порядку загрузки |
| П5 | Пермы занимали личную квоту `maxProps=150` | После десятка пермов игрок не мог спавнить пропы |
| П7 | Права только у суперадмина | Руководство фракций не могло закреплять своё имущество |
| П8 | Не было аудита | Непонятно, кто и когда закрепил объект |

### 16.2. Формат базы v2 и миграция

Файл прежний — `data/grm_perm_entities.json`, структура прежняя (плоский массив).
К записи добавлены поля: `uid`, `ownerKind` (`server|faction|character`), `owner`,
`ownerName`, `faction`, `freeze`, `label`, `by`, `byName`, `at`.

Миграция идемпотентна и выполняется при первом чтении базы (`loadDB`):

1. Если у всех записей есть `uid` — не делает ничего.
2. Иначе пишет бэкап `data/grm_perm_entities.bak.<timestamp>.json` **и проверяет
   его чтением**. Бэкап не подтвердился — миграция отменяется, работаем со старым
   форматом: терять боевую базу нельзя.
3. Старым записям проставляется `ownerKind="server"` и `freeze=true` — это
   **ровно текущее поведение**, поэтому ни один существующий перм не меняет смысла.

### 16.3. Публичный API `GRM.Perm`

| Функция | Назначение |
|---------|-----------|
| `Add(ply, ent, opts)` | Закрепить. `opts = {ownerKind, owner, ownerName, faction, freeze, label}`. Повторный вызов по закреплённому объекту = `Update` |
| `Remove(ply, ent, alsoDelete)` | Снять закрепление. По умолчанию объект **остаётся** на карте (П2) |
| `Update(ply, ent, opts)` | Обновить позицию, данные экземпляра, метку, владение |
| `Info(ent)` / `IsPerm(ent)` | Запись объекта / признак закрепления |
| `ListForMap(map)` | Список закреплений карты |
| `IsPermable(ent)` | Можно ли закрепить + **причина отказа текстом** |
| `CanManage(ply, ent)` | Права на управление конкретной записью |
| `RegisterClass(class, allowed)` | Регистрация класса модулем без правки ядра |
| `SetOwner(ply, ent, kind, value)` | Перепривязка владения |
| `Upsert` / `UpdateEntry` | Псевдонимы старого API — прежние вызовы не сломаны |

Сигнатуры `Add(ply, ent)` и `Remove(ply, ent)` подобраны под существующие вызовы
в `grm_service_tool.lua:156,210`, поэтому **Д17 закрылся без правки того файла**.

Поиск записи по объекту идёт сначала по `uid`, и только затем по «класс +
позиция» — закрепление больше не теряется при сдвиге объекта (П3).

### 16.4. Цепочки делегатов (П4)

`GRM.PermData.Extract` и `.Apply` заменены прокси-таблицами с метатаблицей.
Привычный синтаксис `Extract[cls] = fn` продолжает работать, но теперь
**накапливает** функции:

* `Extract[cls]` — композит: вызывает все делегаты, результаты мержит в одну
  таблицу (ключи верхнего уровня не пересекаются: `ffd` / `sliding` / `prop` /
  `computerName`);
* `Apply[cls]` — композит: вызывает делегаты по очереди, каждый в `pcall`.

Порядок загрузки перестал что-либо решать. **Девять существующих файлов-регистрантов,
включая `ffd_fading_door.lua`, править не потребовалось.**

### 16.5. Синхронизация с проп-протектором

Четыре точки в `sh_grm_prop_protect.lua`:

1. `IsServerEntity` — закреплённый объект серверный, только если `_grmPermKind == "server"`.
   Это и есть исправление П1.
2. Ветка 2.5 в `CanInteract` — фракционные и личные закрепления: владелец
   (или сотрудник фракции с правом `perm_manage`) взаимодействует, `remove`
   запрещён всем, кроме суперадмина. Сначала снять закрепление, потом удалять.
3. `countProps` пропускает объекты с `_grmPerm` — пермы не съедают личную квоту (П5).
4. HUD показывает строку **«★ ЗАКРЕПЛЁН НА КАРТЕ»** с видом владения.

Метки на энтити: `_grmPerm`, `_grmPermKind`, `_grmPermUID`; для клиента —
`GRM_IsPerm` и `GRM_PermKind`.

### 16.6. Инструмент `grm_perm_tool`

## 17. Задача 10: синхронизация счёта, исполнитель услуг, переносы строк

### 17.1. Рассинхрон банкомата и HUD

**Симптом.** Игрок вносил деньги в банкомат, строка «НА СЧЁТУ» в HUD
продолжала показывать старую сумму до перезахода.

**Причина.** Счёт меняли в десятке мест, а `GRM_Bank_Sync` слали в двух:
`E.BankTake` и `E.BankGive`. Ключевые операции банкомата — `E.BankDeposit`,
`E.BankWithdraw`, `E.BankTransfer` — сохраняли данные, но клиенту ничего не
отправляли.

**Решение** (`sh_grm_economy.lua`):

* `pushBank(ply)` добавлен в `E.BankDeposit`, `E.BankWithdraw` и
  `E.BankTransfer` (в переводе ещё и `pushBankBySid(toSid)` — получателю).
* Публичные псевдонимы `E.PushBank(ply)` и `E.PushBankBySid(sid)`: сторонний
  модуль может явно попросить пересинхронизацию.
* **Сторож `GRM_Economy_BankSyncWatch`** — таймер раз в секунду сверяет
  фактический баланс с таблицей `lastPushedBank` (что реально ушло в HUD) и
  досылает разницу. Это страховка от будущих модулей, которые поменяют
  `acc.balance` напрямую в обход API: чинить каждый вызов по отдельности
  хрупко. Трафик копеечный — пуш идёт только при расхождении.
* `PlayerDisconnected` чистит запись игрока из `lastPushedBank`.

`ply._grmBankTouch` проставляется во всех банковских операциях и читается
защитой от потери баланса при перезагрузке `grm_treasury.json`.

### 17.2. Исполнитель услуги

Раньше услуга принадлежала фракции неявно, а в интерфейсе про исполнителя не
было ни слова: было непонятно, куда уйдут деньги за заказ.

**Сервер:**

* `S.ProviderList(category)` (`sh_grm_services.lua`) — список организаций с
  правом оказывать услуги; при переданной категории фильтруется по
  `S.FactionCanService`. Возвращает `name`, `institution`, `canService`,
  `canInvoice`, `maxInvoice`.
* `S.UpsertService` проверяет, что исполнитель указан и такая фракция
  существует; чужого исполнителя может назначить только суперадмин.
* `S.IssueInvoice` проверяет права на `opts.faction`: выставить счёт от имени
  чужой организации может только суперадмин.
* `A.Snapshot` (`sh_grm_atm.lua`) отдаёт клиенту `snap.providers`, а каждая
  услуга в `snap.org.services` — поле `provider`.

**Клиент банкомата:**

* Форма «Добавить / изменить услугу» — ячейка **«Исполнитель услуги»**:
  выпадающий список организаций для суперадмина, read-only подпись со своей
  организацией для лидера фракции. Все поля получили подписи над собой.
* Строка каталога услуг показывает «Исполнитель: …» отдельной строкой.
* Форма «Выставить счёт» — ячейка исполнителя (кому уйдут деньги), явная

  Выбор услуги из каталога подставляет название, цену и исполнителя.
* Витрина услуг — **фильтр по исполнителю** рядом с фильтром категорий,
  исполнитель виден в карточке и в окне подтверждения заказа.

Исполнитель идентифицируется **именем фракции**: одно и то же значение лежит
в `snap.providers[].name` и в `service.provider`.

## 19. Обрезка кириллицы по байтам (задача 12)

### Симптом
В бланке «Мои дипломы» (ГД-2026-000001) значения обрывались посреди слова:

| Поле | Было на экране |
|---|---|
| Учреждение | `Высшая Краснознамённая школа КГБ им. Ф.Э.Дзержинског` |
| Квалификация | `Аналитико-прогностическое и социальное управление (` |
| Подпись | `Ю. Андропов, доцент кафедры государ` |

Выглядело как «не работает перенос строк».

### Настоящая причина
Перенос строк был исправен — до клиента доезжал **уже обрезанный текст**.
`string.sub` режет **байты**, а кириллица в UTF-8 занимает **2 байта на символ**.
Поэтому `trim(s, 96)` оставлял ~48 русских букв, а не 96, и мог разорвать
многобайтовую последовательность пополам, давая битый символ.

Проверка: `#"Высшая Краснознамённая школа КГБ им. Ф.Э.Дзержинского"` = 98 байт
при 53 символах; первые 96 байт заканчиваются ровно на `Дзержинског`.

### Исправление
В `sh_00_grm_ui.lua` (грузится первым) добавлены общие хелперы:

- `GRM.Utf8Len(s)` — длина в символах;
- `GRM.Utf8Sub(s, n)` — обрезка до `n` символов, не разрывая символ;
- `GRM.Utf8Ellipsis(s, n)` — то же плюс «…» для подписей в интерфейсе.

Задействованы в:

| Файл | Что исправлено |
|---|---|
| `sh_grm_diplomas.lua` | `trim()` — все поля диплома (лимиты 96/64 теперь в символах) |
| `sh_grm_services.lua` | `trim()` — названия услуг, назначения платежа, примечания |
| `sh_grm_ctx.lua` | 10 подписей контекстного меню (`GRM.Utf8Ellipsis`) |

Лимиты не менялись — изменилась только единица измерения (символы вместо байт),
поэтому миграция данных не требуется: уже сохранённые записи остаются валидными,
а новые перестают обрезаться.

### Высота бланка
Карточка бланка приклеена через `Dock(TOP)`. Смена высоты изнутри
`PerformLayout` не перестраивает docking сама по себе, из-за чего бланк
оставался фиксированным (250 px), а лишние строки уходили под нижний край.
Теперь после `SetTall(need)` вызывается `InvalidateLayout()` у родителя и
у канваса `DScrollPanel`.

### Регрессионный тест
`tools/luatest/sim_utf8_trim.lua` — 47 проверок: длина в символах, целостность
UTF-8 при любом лимите, реальные строки со скриншота, многоточие, а также
контроль того, что `trim()` в модулях больше не зовёт байтовый `string.sub`.
Тест проверен на «убийство мутанта»: возврат байтовой обрезки даёт 13 провалов.

пропало привычное слово «перм».

| Было | Стало |
|---|---|
