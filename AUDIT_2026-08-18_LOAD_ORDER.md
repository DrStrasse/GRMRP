# АУДИТ НАГРУЗКИ И ПОРЯДКА ВЫПОЛНЕНИЯ — 18.08.2026

Заказ владельца: «Все модули под аудит на микрофризы, на нагрузку,
первостепенные элементы, второстепенные и порядок их исполнения настроить».

Инструмент аудита: `python3 tools/audit_perf.py` (лежит в репозитории, можно
прогонять после любой правки). Он сканирует 505 lua-файлов и ищет четыре
класса проблем:

1. покадровые хуки (`Think`, `HUDPaint`, `SetupMove`, `PostDraw*` …) с
   дорогими вызовами внутри — сканы карты, обходы игроков, трассы, чтение
   файлов, создание материалов;
2. таймеры чаще раза в секунду;
3. `ENT:Think` без `SetNextThink`;
4. старты подсистем мимо планировщика `GRM.Boot`.

Скрипт понимает перф-слой GRM: строка, где используется `GRM.Perf.Entities`,
`GRM.Perf.Players`, change-only NW, нарушением не считается, а хук с ранним
выходом по `CurTime()` весит вдвое меньше.

## 1. Порядок выполнения кода

`GRM.Boot` получил единую точку **`GRM.Boot.OnMapStart(id, tier, fn)`** (v1.1.0).
Все 27 модулей, которые раньше поднимались напрямую через `InitPostEntity` /
`Initialize` (30 хуков), переведены на планировщик. У каждого файла на входе
стоит шим `grmBootStart` — если планировщик почему-то не загружен, модуль
стартует по-старому и ничего не ломается.

Классификация (tier определяет очередь исполнения; выполняется порциями с
бюджетом `grm_boot_budget_ms` — 2 мс/тик на сервере, 3 мс на клиенте):

**early — первостепенное, должно быть готово ДО входа игроков**
- `sh_spawn_points` — точки спавна;
- `sh_grm_factions_core_v4` — миграция структуры организаций;
- `sh_grm_property` — политика дверей собственности;
- `sh_grm_prop_protect` — стабилизация уже стоящих пропов;
- `sh_grm_ctx` — контекстное меню и его реестры.
(плюс из прошлой волны: `doors.identity`, `doors.db`, `perm.entities`)

**normal — обычная игровая логика**
- банкоматы (`sh_grm_atm`), эфир (`sh_grm_broadcast`), радиосеть
  (`sh_grm_radionet`), торговцы (`sh_grm_vendor`), дилер транспорта
  (`sh_grm_vehicle_dealer`), работы (`sh_grm_jobs`), статус пожаров
  (`sh_grm_fire_status`), fading doors (`sh_grm_ffdlink`), сервисы
  (`sh_grm_services`), спецслужбы (`sh_grm_special_service`), штрафы
  (`sh_grm_wanted_fines`), аугментации и чипы, стамина (`sh_grm_movement`),
  патч еды в инвентаре, прослушка помещений (`sv_grm_roomtap`),
  **новый салон связи** (`vendor.phone`).

**late — можно подождать, на старте не нужно**
- прекэш звуков (`sh_07_grm_sound`), дипломы, фикс анимации дилеров,
  клиентские запросы HUD (`GRM_HUD_ReqBal`, `GRM_HUD_Welcome`),
  HUD аугментаций, запрос кастомизации, звук шагов стамины.

**idle — только по требованию** (без изменений с прошлой волны):
магазин телефонии и подобные редкие меню поднимаются по чат-команде,
использованию entity или входу первого игрока.

Проверить в игре: консоль `grm_boot_status` — покажет очередь, тиры,
время каждой задачи и суммарные миллисекунды старта.

## 3. Оставшиеся быстрые таймеры (признаны оправданными)

- `sh_grm_movement` `GRM_StaminaTick` 0.1 c — стамина, 10 Гц, внутри
  change-only синк (`nextSync` 0.25 c). Механика требует такой частоты.
- `sh_grm_doors` 0.2 / 0.3 c — одноразовые (`reps = 1`) отложенные пересборки.
- `sv_grm_handcuffs` `GRM_Stun_<ent>` 0.2 c — живёт только на время стана.
- `sh_grm_radionet` 0.35 / 0.5 / 0.7 c — обходы дешёвые, работают по уже
  собранным спискам, на клиенте — только по говорящим.
- `grm_citadel_core_terminal` 0.5 c — только пока открыто окно терминала.

## 4. Что проверить на живом сервере

1. `grm_boot_status` — суммарное время старта и распределение по тирам;
   если какая-то задача занимает > 20 мс, её стоит опустить в `late`/`idle`.
2. `grm_sound_check` — какие звуки не нашлись (в первую очередь `kom_hour.wav`).
3. `python3 tools/audit_perf.py` — после любых новых модулей.

## 5. Вторая волна (вечер 18.08): распределение нагрузки в рантайме

`GRM.Boot` размазывает СТАРТ карты. Для игрового времени добавлен такой же
механизм в `GRM.Perf` v1.3.0:

| API | Назначение |
|---|---|
| `GRM.Perf.Queue(id, fn[, priority])` | разовая тяжёлая задача выполняется в ближайшем кадре, где есть бюджет |
| `GRM.Perf.Spread(id, list, fn[, opts])` | обход большого списка порциями (`chunk`, `priority`, `onDone`) |
| `GRM.Perf.QueueStatus()` / `grm_perf_queue` | что сейчас в очереди |
| конвар `grm_perf_budget_ms` | бюджет на кадр (1.5 мс сервер / 2 мс клиент) |

Планировщик засыпает при пустой очереди, повторная постановка обхода с тем же
`id` заменяет прежний (обходы не копятся при частых событиях).

Первое применение: обновление ключей транспорта (`sv_vehicle_keys`) на полном
сервере теперь размазывается по кадрам вместо одного прохода по всем игрокам.

### Детектор фризов

`grm_perf_report` — сводка: сколько кадров/тиков измерено, среднее и
максимальное время, последние всплески. В момент всплеска (порог —
`grm_perf_spike_ms`, по умолчанию 40 мс) фиксируется срез: игроки, сущности,
количество машин **включая simfphys и LVS**, число задач в очереди GRM.
`grm_perf_reset` — сбросить статистику.

Это отвечает на главный вопрос по транспорту: если всплески идут при большом
числе `gmod_sent_vehicle_fphysics_base` / `lvs_base`, дело в физике машин, а не
в логике GRM — и это видно из отчёта, а не на глаз.

### Порядок диагностики на живом сервере

1. `grm_boot_status` — сколько заняла загрузка и какая задача самая дорогая.
2. `grm_perf_report` — есть ли всплески и что было в этот момент.
3. `grm_perf_queue` — не копится ли очередь (значит, бюджет мал или задача тяжёлая).
4. `python3 tools/audit_perf.py` — статический аудит после любых правок.

## 6. Модуль анализа нагрузки (GRM Analytics v1.0.0)

`lua/autorun/sh_grm_analytics.lua` — постоянный сбор телеметрии раз в секунду
плюс профилировщики по требованию.

**Что читает постоянно**
- тайминги тика/кадра, всплески, размер очереди фоновых задач;
- сущности: всего, GRM, пропы, транспорт (**отдельно simfphys и LVS**),
  активная физика (не спящие объекты), разбивка по классам;
- двери: всего, с записями GRM, бесхозные, парные и **подозрение на фантомы**
  (лишние entity в группах дедупликатора);
- игроки: пинг, скорость, пройденное расстояние, [E], выстрелы, смерти,
  спавны, чат, в транспорте / ноклипе / мёртв / на службе / AFK;
- события: `player.use`, `door.use`, `entity.created`, `prop.created`,
  `chat.command`, `fire.incident`, `arrest.change`, `duty.change`,
  `vehicle.spawned` и т.д. — за минуту и за сессию.

**Профилировщики (только по команде, на 3–60 с)**
- `grm_analyze_hooks 10` — сколько миллисекунд съел каждый хук GRM и сколько
  раз он вызывался (оборачиваются только наши хуки, потом возвращаются);
- `grm_analyze_net 10` — какие net-строки шлют больше всего пакетов и байт.

**Команды**

| Команда | Что показывает |
|---|---|
| `grm_analyze` | общая сводка: тайминги, сущности, двери, игроки, топ событий |
| `grm_analyze_ents` | сущности по классам (топ 25) |
| `grm_analyze_doors` | двери и фантомы + что делать |
| `grm_analyze_players` | таблица по игрокам: движение, действия, состояние |
| `grm_analyze_events` | счётчики событий и последние профили |
| `grm_analyze_dump` | полный срез в `data/grm_analytics/report_*.json` |

Всё это доступно и кнопками: `/admin` → **«Анализ нагрузки»**.

## 7. Важно про детектор фризов: ложные срабатывания устранены

Первый живой прогон дал пачки ровно по ~50 мс при среднем 5 мс. Это **не
фризы**: GMod при потере фокуса окна рендерит на ~20 Гц, и дельта кадра
становится 50 мс. Детектор теперь пропускает такие кадры и считает их
отдельно:

- окно свёрнуто / нет фокуса (`system.HasFocus`);
- открыто игровое меню (Esc);
- первые 15 секунд после загрузки (прогрев);
- мир ещё не готов.

В отчёте появились: число отфильтрованных кадров, средний FPS, свёртка пачек
одинаковых всплесков (`x12`) и колонка **какие окна GRM были открыты** в
момент рывка — чтобы сразу видеть, виновато ли меню.
